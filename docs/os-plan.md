# rvsim 图形界面重做方案

> 三份独立调研（架构 / 视觉 / 风险评审）的汇总。
> 前两份给方案，第三份专门挑毛病。**本文档只列结论和分歧，细节见各自原始报告。**

## 一、诊断：为什么现在难看、难用

三方独立得出的结论高度一致，按严重程度排序：

### 1. 字体不是「不好看」，是「根本不是字体渲染」
内核对每个字符画 **8×16 = 128 个二值点**（ASCII）或 16×16（汉字），全屏零抗锯齿。
再叠加 **1.2734 倍非整数缩放 + `image-rendering:pixelated`**，笔画在 1px/2px 之间跳变。

实测：ASCII 显示尺寸 10.19×20.38px、汉字 20.38×20.38px ——
**看着是 20px 正文，实际只有 8×16 的字形信息量**，等于把 11px 的 VGA 字拉到 20px。

### 2. CSS 里写的字体，这台机器上根本不存在
像素签名法实测（`document.fonts.check` 会误报）：
- ✅ 有：`Segoe UI Variable Text`、`Cascadia Mono`、`Cascadia Code`、`Consolas`、`DengXian`
- ❌ 没有：`JetBrains Mono`、`Sarasa Mono SC`、`Noto Sans Mono CJK SC`、`Inter`

**等于没写**。中英最终来自两个不相干的 fallback。

### 3. 布局没有系统，是死坐标
| 实测问题 | 数字 |
|---|---|
| 桌面丢 50px（`main{height:calc(100% - 50px)}` 与 `header{display:none}` 打架） | 底边不贴屏幕 |
| Terminal 内容填充率 | **12%** |
| Monitor 底 378 vs Files 顶 332 | **重叠 46px** |
| Terminal 右 885 vs Monitor 左 886 | **1px 缝** |
| 右下留白 | 172 / 161px |

### 4. 交互：命中区太小、可拖区太窄
- **只有 36px 标题栏能拖，窗口 93% 的面积拖不动** —— 用户抓的正是内容区，所以感受是「完全拖不动」
- 窗控点 **10×10 = 100px²**，Win11 是 46×32 = 1472px²，**小 14.7 倍**
- 窗控点在右侧却用 macOS 红黄绿：**位置抄 Windows、配色抄 macOS，两边都不像**
- **开始菜单真的坏了**：点汉堡后 `#startMenu` 未进 DOM（实测 null）
- 关闭按钮时灵时不灵：连点 3 次，第一次关不掉

### 5. 缺少的视觉元素（「没有」比「不好看」更致命）
桌面图标（**0 个**）· 可用开始菜单 · 系统托盘（只有时钟）· 桌面右键菜单 ·
任务栏运行指示条 · 窗口聚焦的强视觉 · 通知 · 空态引导 · 图标体系（只有 `▣◫▤`）· 设置页

### 6. 开机画面是假的
- 只覆盖 `y≥50`（`#splash{inset:50px 0 0 0}`）→ **不是全屏**
- 调试齿轮 `z-index:60` 压在 `#splash`(40) 上 → **开机时能看见一个 ⚙**
- 内容是无限滑动条 → **那不是进度，是装饰**
- 3.5s 后桌面直接出现，没有入场

### 7. 壁纸被自己弄脏
`#wallpaper::after` 是 3px 间距的白点阵、`opacity:.35`，1440 宽每行 480 个点 ——
放大看是**规则方格网，像纱窗/摩尔纹**，把本来还行的双光晕全毁了。

## 二、三条已确认的硬事实

### 1. 我提交过「桌面图标」，但它从来没显示过
`878cc6e` 的 14 行全在 `wall_build()` 里，而这个函数在 `6cfcb67` 就失去了唯一调用者。
**功能提交了、没生效、三天没人发现**，因为：

> `tests/` 只有 riscv-tests（91 项，指令层）和 `contract.js`（18 项，UART 文本）。
> **没有一条测试看界面。**

这是「三个窗口关掉后桌面全空」的直接原因。

### 2. 有一大堆死代码在空转
- `g_wall[800*600]` = **1.92 MB**，占 bss 的 **92.7%**
- `wall_build()` / `fb_plane()` 零调用
- `#screen` canvas 已 `display:none`，`screenRender()` 每帧仍被调用、永远直接返回

### 3. 每帧的渲染代价比模拟本身贵 2-3 倍
`winSync()` 每帧无脏检查地 `createImageData` + 逐像素 + `putImageData`：
- 322,608 像素/帧 = **1,290,432 B ImageData/帧**
- 60fps × 1.23 MiB ≈ **74 MiB/s 的临时分配**
- 估算 **2–3.6 ms/帧**，而常驻档 `stepBudget` 只有 1 ms

**这就是「拖动和输入时好时坏」的真正来源——不是循环慢，是 GC 在拖帧。**

## 三、方案分歧（需要拍板）

### 分歧点 1：终端要不要换成 DOM（真字体）

| | 保留点阵（内核画） | 换成 DOM（宿主渲染） |
|---|---|---|
| 字体观感 | **天花板极低**，8×16 无解 | 真字体、可选中、可滚动 |
| 「kernel 驱动图形」卖点 | 保留 | **弱化**（只剩 Monitor/Files 两个表格） |
| 工程量 | 0 | 约 16 人时 |
| 风险 | 无 | CJK 列宽对齐（见下） |

**风险评审的核心反对**：
> 需求是「字体」，方案是「重写整个呈现层」，方案比需求大一个数量级。

**视觉评审的核心判断**：
> 不做这条，前五件做完仍是「一个好看的 IDE」；做了才是「一个操作系统」。

**我的倾向**：终端换 DOM，但 **Monitor/Files 保留内核绘制**，这样 `fb_text` 仍有使用者，
「guest 光栅化」随时可以现场演示，卖点不至于归零。

### 分歧点 2：一次性重做 vs 分步

**架构方案**：五步迁移，每步可用。
**风险评审**：反对「一次性重做」，要求先删死代码、先立契约、先补测试。

**倾向**：接受风险评审的顺序。理由来自 git log 的事实：

| 事实 | 数字 |
|---|---|
| 最近 20 提交 | 9 feat / **8 fix** —— fix 占 **40%** |
| 窗控点改了几次 | 3 次（`4e06e56` → `0d2a007` → `11f0a36`） |
| 终端重绘改了几次 | 3 次（`df8bda2` → `94b7dd6` → `37f710c`） |
| 前端体积 | 20 KB → **52 KB（2.56 倍）**，就在这 14 次提交里 |
| 回滚次数 | **0** |

**「修 A 坏 B」不是运气，是没有验证面。**

### 分歧点 3：事件流接口做不到

架构方案想暴露事件流，但：
- `0x83FFE000` 附近**可用余量只有 7.9 KB**
- 事件流 **16384 × 24 B = 393 KB**，是余量的 **49 倍**

**结论：事件流必须留在原地，发现页只报地址**（架构方案后来也改成这样了），
否则要重排整个内存图。

## 四、推荐执行顺序

### 阶段 0：清理（0.5 天，零风险，先做）
- 删 `g_wall` / `wall_build` / `fb_plane` / `#screen` 路径与每帧 `screenRender()`
- **收益**：bss 减 1.92 MB；`page_alloc` 可用空间从 1.88 MB 提到 ~3.75 MB
- 修 `page_alloc` 上限 `0x80400000` → 严格低于内核栈顶（现存隐患）
- **验收**：`make` 通过、三个窗口照常、可见行为零变化

### 阶段 1：外壳 80 分（1 天）
按视觉方案的性价比排序：
1. **配色重置 + 壁纸重做**（0.5h）：换 token、删 3px 点阵、光斑压到 .10/.14
2. **字体阶梯**（1h）：删掉不存在的字体、11.5/10.5px 全升到 12/14、中文行高 +2、数字 tabular-nums
3. **窗口外壳**（2h）：标题栏 36→32px、46×32 三键（热区放大 14.7 倍）、四级阴影、整条标题栏可拖
4. **桌面图标 + 开始菜单**（4h）：6 个图标能开窗、开始菜单修好
5. **任务栏重做**（3h）：54→48px、居中图标、16×3 指示条、真实托盘

**验收（可截图比对）**：
- 关完三个窗口后桌面仍有 6 图标 + 可用开始菜单 + 可用任务栏
- 任意文字 ≥12px、无 11.5/10.5px
- 窗口无 1px 缝、无 46px 重叠
- 关闭按钮能命中

### 阶段 2：终端真字体（2-3 天）
- 内核导出终端网格（码点 + 属性 + 行版本号 + 光标状态）到独立一页
- 宿主用 DOM 渲染 22 行，真字体
- **必须同时解决 CJK 列对齐**（字体度量不保证汉字 = 2ch，要显式 `width:2ch` 或 CSS Grid）

**验收**：
- `dumpterm` 的 22 行 === DOM 的 22 行，逐字相等
- 中英混排**逐列对齐**
- 最大化窗口后文字**不变糊**（不再拉伸位图）

### 阶段 3：面板 DOM 化 + 界面测试
- Monitor/Files 改 DOM 表格
- **补界面测试**（这是唯一缺口，比方案本身重要）：
  - `dumpterm` 与共享区逐字符比对
  - `ps` 与进程表比对
  - 事件 seq 单调
  - headless DOM 断言（22 行文本 == 网格）

### 阶段 4：开机动画与过渡（1 天，全在宿主）
- splash 改成**真实进度**（wasm 下载/实例化/kernel boot 加权），不是无限滑动
- 全屏覆盖、隐藏调试齿轮、最少 1.2s / 最多 3.2s
- 桌面入场：壁纸先出，窗口 stagger 60ms

## 五、三个最可能翻车的地方

### 1. CJK 宽度对齐（最可能翻车）
现在汉字占 2 格 = 16px 是**内核用像素保证**的。换 DOM 后字体度量**不保证** 2ch。
表现：一旦某行有中文，后面所有列错位。
**最危险的地方：纯 ASCII 自测永远通不过，只在混排时出现。**

### 2. 跨语言 ABI 错位，且不报错
前端硬编码 `i * 11` 和 `A[b+6]`。加字段不改前端就是**静默画错**——已经发生过一次
（`11f0a36` 加 `win_w/win_h`，前端还在读旧的）。
**对策**：结构体带头 `{magic, version, seq, len}`，版本不符直接回退并显示提示，绝不静默。

### 3. 撕裂 + wasm HEAP 视图失效
- 撕裂：宿主读、内核写交错，用 seqlock（奇数=写入中，前后不等就丢弃本次）
- `ALLOW_MEMORY_GROWTH=1`：内存一旦增长，之前取到的 `HEAPU32` 会 detach
  → **绝不能把 TypedArray 缓存在闭包里跨帧使用**

## 六、我的建议

1. **先做阶段 0 和 1**（1.5 天），这两阶段风险低、观感提升大，做完桌面就不像 IDE 了。
2. **阶段 2 单独决策**——它决定天花板，但有 CJK 对齐的风险，且工程量大。
3. **界面测试必须补**，否则做完还是「提交了没生效，三天没人发现」。
