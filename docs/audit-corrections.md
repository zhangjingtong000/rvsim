# 审计修正记录

一次独立审计（只读、实际运行、不采信文档）对本项目下了严厉结论：

> **没有达到预定目标，且目标定义本身有缺陷。**

本文诚实记录：哪些成立、修了什么、还剩什么没修。

---

## 一、审计核实成立的四个硬伤（已修）

| 问题 | 实测证据 | 根因 |
|---|---|---|
| `run badptr` 后 `run hello` 仍跑 badptr | `denied` 从 6 涨到 12 | `g_badptr_flag=0` 写在 `kernel_apply_run` 之后，而该函数进用户态不返回，那行是死代码 |
| `assert uart=ZZZ_NEVER_12345` 返回 true | 该串从未被系统输出过 | 滑动窗口下绝对位置 `g_cmd_mark` 失效，查到的是自己的命令回显 |
| `run fork` 后 `spawn` 只有 3 条 | `ps` 显示 4 个进程 | fork 创建子进程时没调 `evt_emit(EVT_SPAWN)` |
| `plan run zzz` 静默跑默认程序 | 无任何错误输出 | `kload_prog` 对未知名字静默回退到默认镜像 |

**这四条都已修复并有测试覆盖**（见 `tests/contract.js` 的 T4/T5/T6/T7）。

## 二、审计推翻的、我之前的错误结论

### 错误结论 1：「第四轮零 bug → 实现层收敛」

`docs/inspection-4rounds.md` 写过这句话。**它是错的。**

四轮巡检花掉 1,096,375 token，只验证了「命令名被调用过」，没有验证「行为是否正确」。
上面那四个硬伤，四轮里一个都没发现。

**错在把「没人抱怨」当成了「没问题」。**

### 错误结论 2：设计文档的自评全是 ✅

`docs/design-ai-os.md` 给「可验证/可回滚/可诊断/幂等」打了全绿勾。实测：

| 自评 | 实测 |
|---|---|
| 可验证 ✅ | `assert spawn=3` 在 4 进程系统上为 true |
| 可回滚 ✅ | 只恢复进程表，内存/代码未恢复 |
| 可诊断 ✅ | 能力层错误没有 `code` 字段，只有 `why` 字符串 |
| 幂等 ✅ | `apply` 是一次性消费，第二次报「计划不存在」——这是 at-most-once，不是幂等 |

**自评与证据脱节，这是最该警惕的自欺。**

### 错误结论 3：实验的「真值」是循环的

`docs/experiment-2026-11-05.md` 写「真值由实验者从事件流独立核对」，
但核对本身用的就是 `log`，而 B 组的 `assert` 也来自同一个 `log`。

**B 组 3/3 只证明「模型学会了查同一个计数器」，不证明计数器正确。**
fork 实验已经证明 `spawn` 计数曾经是错的。

## 三、审计指出但尚未修的问题（诚实列出）

按严重程度：

### 1. 事件流不是完整真相

- `EVT_CAP=512` 环形覆盖，满了丢最旧 → **与文档「append-only 不可篡改」直接矛盾**
- 只记录 `spawn`（fork 已补）/`exit`/写类 `ecall`/`restore`
- `sbrk`/`getpid`/`yield`/`reset`/`snapshot`/`plan`/`apply` 全无事件
- **没有任何 replay / 状态重建实现**，而设计文档把它列为派生性质

**影响**：一个信任这套接口的 agent 会得到「spawn=3 但实际 4 个进程」这类自信的错误结论。

### 2. `snapshot` 只恢复进程表

- `snap_t` 只有 `proc_t procs[NPROC]`，不含用户内存、代码页、页表
- 实测：存档 → `run fork` → `restore` 后，`0x80400000` 仍是 fork 代码
- 已加 `resume` 让进程能被再次调度，但**内存不一致的问题仍在**

**影响**：「恢复到存档时的状态」这句话目前只对了一半。

### 3. 人机接口不平等

前端直接读写 WASM 状态：

```js
M._rv_reg(i) / M._rv_set_reg(i, v) / M._rv_set_pc(v)
```

人可以逐个查看和修改 32 个寄存器，**AI 连读寄存器都没有能力**。

这违反设计原则「单一权威接口，所有客户端平等」。

### 4. 项目门面过时

`README.md` 仍停在 2026-10-26 的旧项目叙事：
写「82/82 全通过」（实测 91/91）、「2,284 + 1,139 行」（实测约 4,065），
且 grep 不到 `manifest`/`事件流`/`assert`/`snapshot`。

## 四、目标定义本身的问题

原目标四条：

```
1. 每个能力都能被调用
2. 每个能力都能被发现
3. 能力能组合起来完成真实任务
4. 人和 AI 走同一套接口
```

**审计指出：这是把「完整使用」定义成了「命令可调用 + 可发现 + 能串起来 + 两端同源」，缺少五个关键维度：**

| 缺失 | 后果（本项目已发生） |
|---|---|
| **语义正确性** | 能调用 ≠ 行为与声明一致（四个硬伤） |
| **独立 oracle** | assert 与被测事件流同源，假阳性无法发现 |
| **误用语义** | 无参数校验（已修部分）、无取消、无超时 |
| **可用性验收线** | 目标没写步数/token/错误恢复率的门槛 |
| **外部判据** | 「在声明的能力集内完整」是自指同义反复 |

**修正后的目标应该是：**

1. 对内核实现的每一条 syscall / 状态转移，存在一个 AI 可触发、可观察的能力
2. 每个能力的行为与 manifest 声明一致，且有**自动化契约测试**
3. 存在一个**不依赖被测事件流**的 oracle
4. 误用、失败、回滚、取消都有明确语义和测试
5. 用**真实任务**（含独立 oracle）定义「完整」，而不是用实现自己声明的能力集

## 五、这批修复的教训

**审计发现的问题分三类，我的应对方式完全不同：**

| 类型 | 例子 | 正确做法 |
|---|---|---|
| 实现 bug | `run` 标志泄漏、`assert` 假阳性 | 修代码 |
| 声明不实 | `run` 说 3 个进程实际 4 个 | 修描述或修实现 |
| 表达能力不足 | `log` 的列语义装不进 desc | 分层（manifest/guide/docs） |

**之前的错误是：把第一类当成第三类处理**——用写文档代替修代码。

`guide` 值得写，但它解决不了「`assert` 会说谎」。
