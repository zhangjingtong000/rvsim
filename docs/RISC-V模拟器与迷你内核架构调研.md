## A.2 指令分发是怎麼做的？（本报告最重要的技术发现）

**答案：三者都有，但层次分明——不是"哪个"，而是"四层"**【实测】

1. **解码层：生成出来的嵌套 `switch` 决策树**
   `decode.c` 里没有大表，而是 `scripts/gen-decoder.py` 按约束（`1..0=` 作根 switch、`6..2=` 次层、`14..12=`…）**生成嵌套 switch**，产出扁平的 `rv_insn_t`：
   ```c
   typedef struct { uint16_t opcode; uint8_t rd, rs1, rs2; int32_t imm; uint32_t pc;
                    rv_insn_impl_t impl; ... } rv_insn_t;
   ```
   `docs/decoder-generator.md` 明说：*"For 32-bit instructions, identification uses nested switch statements on the opcode, funct3, and funct7 fields."*（第 67–70 行）作者还专门写了 `scripts/verify-tree.py` 校验决策树叶子数 == 描述表行数，避免"某条指令被静默丢掉"。

2. **分发层：预解析函数指针表，不是运行时 switch**
   `emulate.c:2648` 的 `insn_handler()` 返回 `dispatch_table[ir->opcode]`，结果**在解码阶段就写进 `ir->impl`**；执行时直接 `impl(rv, ir, &cycle, &pc)`。也就是说：**每个指令字只查一次表，之后热循环里连 switch 都不做**。

3. **块层：block chaining / superblock**
   `rv_step()` 把连续指令串成 block，块尾直接跳下一块，减少分发次数。

4. **JIT 层（可选编译）**：热块提升为本地机器码（x86-64/ARM64）。

**自动生成工具链**【实测】：`Makefile:403-427`
```
DECODER_DESC := src/instructions.in
DECODER_GEN  := scripts/gen-decoder.py
src/decode.c: $(DECODER_DESC) $(DECODER_GEN)   → 生成到临时文件，clang-format 后再 move
make check-decoder:                            → 重新生成并 diff，防止提交的 decode.c 与描述表漂移
```
`decode.c` 是"既生成又提交"的——这是为了让 clone 下来不装 clang-format 也能编译，同时让解码器改动能在 PR 里 review。**这个取舍值得学**。

**给你的建议**：7,300 行预算下，**只学第 1+2 层的思想**（解码产出 IR → 执行消费 IR），实现上用一个 `switch(opcode)` 穷举 + 一张小小的 imm 提取函数表就够了。生成器（`gen-decoder.py` 1,218 行）会把你拖进"写工具链"而不是"写模拟器"的坑。

## A.3 外设模型怎么组织

三层，全部靠宏和 `#if`【实测】：

1. **地址路由**（`src/system.h`）：`MMIO_READ()` / `MMIO_WRITE()` 宏里先判 `(addr>>28)==0xF`，再取 `hi=(addr>>20)&0xFF`（256 个 1MiB 槽），`switch(hi)` 落到具体设备。VIRTIO 设备是动态枚举的（`vblk_mmio_base_hi`），因为块设备数量可变。
2. **设备操作**（`src/system.h:45` 的 `MMIO_OP(io, rw)`）：一个巨型 `switch`，每个 case 里用 `IIF(rw)(读, 写)` 在**编译期**选读写分支；每次访问后立刻调 `emu_update_xxx_interrupts()` 把设备电平推到 PLIC。
3. **设备实现**（`src/devices/*.c`）：每个设备是"胖结构体 + `xxx_read/xxx_write(dev, offset, val)`"，**没有统一 vtable**。

中断聚合的写法很直白，值得抄它的"显式中断线"思路：
```c
void emu_update_uart_interrupts(riscv_t *rv) {
    u8250_update_interrupts(attr->uart);
    if (attr->uart->pending_intrs) attr->plic->active |= IRQ_UART_BIT;
    else                           attr->plic->active &= ~IRQ_UART_BIT;
    plic_update_interrupts(attr->plic);
}
```

**代价**：加一个新设备要改 3 处（`SUPPORTED_MMIO` 枚举、`MMIO_OP` 分支、`MMIO_READ/WRITE` 的地址映射），且都在同一个头文件里。**这是 C 宏风格的典型技术债，项目别学**。

## A.4 GDB stub 怎么接的

- `src/gdbstub.c` **只有 200 行**，是纯适配层：`rv_read_reg` / `rv_write_reg` / `rv_read_mem` / `rv_write_mem` / `rv_debug_should_stop` / `rv_get_reg_bytes`。
- RSP 协议本身在**子模块** [RinHizakura/mini-gdbstub](https://github.com/RinHizakura/mini-gdbstub)（`.gitmodules` 里声明）。
- 走 TCP socket，`rv32emu -g <elf>` 启动后在 `:1234` 等 `target remote`。要求 `ENABLE_GDBSTUB` 编译开关（默认 defconfig **不开**）。
- 另有 `-d <file>` 把寄存器 dump 成 JSON，用于测试与前端。

**给你的建议**：GDB RSP 的价值是"能接 VS Code / gdbgui"，但它是一条**文本协议的坑**（握手、`qXfer`、`vCont`、断点续传）。你既然要自己做可视化界面，**更应该暴露一个自己定义的 JSON 快照协议**（`{pc, regs[32], csr{}, mem窗口, 每指令状态}`），前端直接画。想做"标准调试器"再接 RSP 不迟。

## A.5 值得学 / 不该学

**值得学（4 条）**
1. **解码与执行彻底分离**：`decode.c` 产出纯数据 `rv_insn_t`，`emulate.c` 只消费它。你的模拟器照这个切，可视化界面就能直接复用 `ir` 做"指令解释"展示。
2. **指令语义单点维护**：语义只写一遍（`RVOP`），解释器/JIT 都从这里取。你只需学到"语义集中在一个文件、按扩展分组"即可。
3. **设备 → PLIC 的显式中断线函数**：一行 `IRQ_UART_BIT` 置位，比"到处 if 检查设备状态"清晰得多。
4. **文档即规范**：`docs/decoder-generator.md` **370 行**，把描述表格式、扩展方法、边界情况、验证命令（`make check-decoder`）全写死。**你的项目设计文档可以直接照这个结构写章节**——这是本项目最该抄的东西，比代码值钱。

**不该学（5 条）**
1. **15,040 行 JIT/AOT**（`jit.c` 6,048 行为代表）。你的 7,300 行连它的翻译器都装不下。
2. **`io.c` 的需求分页后端**：`SIGSEGV` 里翻页 + `madvise` 回收 + 4GiB 镜像。不可移植（Windows 上没有等价物）、崩溃时栈几乎不可读。项目用 `malloc` 一大块 RAM 即可。
3. **向量扩展 6,931 行**：`rv32_v_template.c` 比你的整个项目还大。
4. **`RV32_HAS(...)` 宏矩阵**：`configs/` 下实测有 **10 个 defconfig 变体**（`defconfig` / `interpreter` / `jit` / `mini` / `system` / `system_interpreter` / `system_jit` / `wasm` / `wasm_system` / `ci`）× 满屏 `#if`，读代码时永远不知道"当前到底编译进了什么"。你要用就行，别学它的可选性设计。
5. **协程 hart（`coro.c` 660 行）**：为了在浏览器里能暂停。你用"每步一个函数 + 状态机"就够。

# B. mini-rv32ima（cnlohr/mini-rv32ima，单文件头）

仓库：<https://github.com/cnlohr/mini-rv32ima>
License：**MIT**（`Copyright (c) 2022 CNLohr`）【实测】

## B.1 它凭什么能用 1,000 行跑起 Linux？

先校正行数【实测】：
- `mini-rv32ima/mini-rv32ima.h` = **548 行**（非空非注释 **445 行**）
- `mini-rv32ima/mini-rv32ima.c`（demo 宿主）= 457 行
- `mini-rv32ima/default64mbdtc.h`（内嵌 DTB）= 97 行
- 三个加起来 1,102 行，与"约 1,000 行"的说法吻合

**真正的原因只有一个：它不做 MMU。**【实测，README 第 32 行原文】

> "I'm working on a really really simple C Risc-V emulator. So simple it **doesn't even have an MMU**."

配套条件是：
1. 跑的是 Linux 的 **nommu 配置**（`qemu_riscv32_nommu_virt_defconfig` + buildroot 补丁，`configs/` 里有全套 buildroot/busybox/kernel config）——内核直接物理地址运行，**不需要 Sv32 页表遍历、不需要 S 模式切换 satp**。
2. 外设只有三样：CLINT（`mtime/mtimecmp`，用宿主微秒数喂）、8250 UART、syscon（几个魔数寄存器）。
3. DTB 编译成 C 数组直接塞进 RAM（`default64mbdtc.h`），省掉 FDT 解析器。
4. 没有 libc 依赖，`MINIRV32_LOAD4/STORE4` 宏直接指针解引用。

**这对你的项目是决定性的**：你的目标是"特权级/CSR/异常 → 启动 Linux"，而且后面还要"页表 + U 模式 + 自制内核"。这恰恰是 mini-rv32ima **故意砍掉**的部分。

## B.2 它明确放弃了什么（README 原文）

| 放弃项 | 出处 | 影响 |
|---|---|---|
| **MMU** | README:32、Q&A:72-73（"Should I add an MMU? **No.**"） | 无 Sv32，无 U 模式隔离 |
| 规范里的绝大多数内容 | README:16 "Is **incomplete** in that it didn't implement the tons of the spec that Linux doesn't (and you shouldn't) use" | 只实现"Linux 用得到的" |
| **RV32A 与 Zifencei 是存根** | README:24 "†: Zifence+RV32A are **stubbed**" | 多核系统无法正确模拟（AMO 语义是假的） |
| 多处理器 | 同上 | 单 hart only |
| 可重定位 ELF | README:98 "Support for relocatable ELF executables" 列为"hopeful goals" | 只能加载 flat binary |
| OpenSBI | README:156 "This does not currently work!" | 无 M 模式固件层 |

## B.3 单文件结构对项目的启发（以及为什么不能照搬）

**可取的部分**——它的宏注入点设计是这个项目最值钱的地方【实测，README:83-93】：

```c
#define MINIRV32_IMPLEMENTATION                // STB 风格：一个头文件，宿主定义它才展开实现
#define MINIRV32_POSTEXEC(pc, ir, retval)      // 每步执行后的钩子 → 做异常/调试追踪
#define MINIRV32_HANDLE_MEM_STORE_CONTROL(...) // 非 RAM 写 → 宿主实现 MMIO
#define MINIRV32_HANDLE_MEM_LOAD_CONTROL(...)  // 非 RAM 读
#define MINIRV32_OTHERCSR_WRITE(csrno, value)  // 未实现 CSR 的写 → 宿主做 syscon
#define MINIRV32_OTHERCSR_READ(csrno, value)
```

**思想**：核心不实现设备和调试，只留 8 个宏当"接口"，宿主 `mini-rv32ima.c` 里全部实现。于是核心 445 行，宿主 457 行，职责一刀切开。

**不可取的部分**：
- 状态是你的全局变量：`#define CSR(x) state->x` 直接映射结构体字段，**没有任何位域抽象**。`mstatus` 的 MIE/MPIE 靠 `(mstatus & 0x08) << 4` 手工移位。
- 异常用整数编码 hack：`trap = cause + 1`，`trap & 0x80000000` 表示中断，末尾 `pc = mtvec - 4` 再 `pc += 4`。**能跑，但你写设计文档时无法解释"为什么这么设计"**。
- 单文件 + 宏 = 无法单元测试。你想给导师演示"CSR 写非法值触发异常"，在这个结构里只能整体跑。
- 加到 7,300 行（你要加 MMU/U 模式/进程/可视化）时，单文件会变成灾难。

**结论**：单头文件是**分发形态**的选择，不是**架构**的选择。你的 7,300 行应该学它的"宏/函数指针钩子"，用**多文件**组织。

## B.4 它怎么处理 CSR、异常、定时器

**CSR**【实测，`mini-rv32ima.h:339-390`】：
```c
case 0x73: // Zicsr
  uint32_t csrno = ir >> 20;
  switch (csrno) {
    case 0x300: rval = CSR(mstatus); break;   // 手写 9 个
    case 0x341: rval = CSR(mepc);    break;
    ...
    default: MINIRV32_OTHERCSR_READ(csrno, rval);  // 其余全交宿主
  }
  switch (microop) { case 1: writeval = rs1; break;   // CSRRW
                     case 2: writeval = rval | rs1; break; ... }
```
只硬编码 Linux 真正用到的 9 个 CSR，其余走宏。**没有 swizzle、没有 CSR 地址表、没有只读/可写位掩码**。

**异常**【实测，`mini-rv32ima.h:141-536`】：
- 主循环内任何异常只做一件事：`trap = cause + 1; break;`
- 循环外统一处理：写 `mcause/mtval/mepc/mstatus`，`pc = mtvec`，清 `trap`
- 同步异常时 `pc` 回退（`SETCSR(pc, pc)` 后再 `pc += 4` 的抵消技巧）保证重新执行
- 永不进入 S 模式：`CSR(extraflags) |= 3` 只是"当前特权 = M"的标记位

**定时器**【实测，`mini-rv32ima.h:124-135`】：
```c
uint32_t new_timer = CSR(timerl) + elapsedUs;   // 宿主把"这轮过了多少微秒"传进来
if (new_timer < CSR(timerl)) CSR(timerh)++;
CSR(timerl) = new_timer;
if (timer* > timermatch* && (timermatchh || timermatchl)) {
    CSR(extraflags) &= ~4;      // 清 WFI
    CSR(mip) |= 1<<7;           // 置 MTIP
}
```
**不建模 CLINT 寄存器**，`mtime` 只是个两段计数器，WFI 就是"提前 return 1"。这比 rv32emu 的 CLINT 设备简单一个数量级——**你的 CLINT 可以照这个写**（IRQ 只做 MTIP/STIP 两条）。

## C.2 流水线可视化的数据从哪来（关键问题）

**答案：模拟器只暴露一条极窄的接口——"某个流水段里现在是哪条指令"。**【实测】

接口定义在 `src/processors/interface/ripesprocessor.h`：
```cpp
struct StageInfo {                          // 第 20 行
    unsigned pc = 0;
    bool stage_valid = false;
    // ... 处理器可附带的其他信息
};
struct StageIndex : public std::pair<unsigned, unsigned> { };  // {lane, stage}
struct ProcessorStructure { unsigned lanes, stages; };         // 第 50 行注释：{#lanes : #stages}

virtual unsigned int getPcForStage(StageIndex) const = 0;      // 第 191 行
virtual QString      stageName(StageIndex) const = 0;          // 第 194 行
virtual StageInfo    stageInfo(StageIndex) const;              // 每条指令的段信息
```

消费端在 `src/pipelinediagrammodel.cpp`（191 行）：
```cpp
connect(ProcessorHandler::get(), &ProcessorHandler::processorClocked,
        this, &PipelineDiagramModel::processorWasClocked, Qt::DirectConnection);  // 第 28 行
...
void PipelineDiagramModel::processorWasClocked() {
    if (m_atMaxCycles) return;              // 封顶后立刻返回（长跑时零开销）
    gatherStageInfo();                      // 每 clock 采集一列
}
// 行 = 指令地址（headerData 里 indexToAddress），列 = cycle 序号
```
`src/instructionmodel.cpp:32` 同理：`m_stageInfos[idx] = ProcessorHandler::getProcessor()->stageInfo(idx);`，用来在反汇编视图里给每条指令标"现在处在 IF/ID/EX/MEM/WB 哪一段"。

**所以答案是**：模拟器需要暴露
1. `numStages()` / `stageName(i)` —— 段的元数据（前端画表头用）
2. `stageInfo({lane, stage}) → {pc, valid}` —— 每个 clock 后的一段快照
3. 一个 `clocked` 事件/回调 —— 让前端知道"该采样了"

**这一个设计（窄接口 + 事件驱动采样 + 前端自己攒时间轴）就是我建议你抄的东西。** 你的模拟器可以暴露 `GET /state` 或 `postMessage({pc, stage, regs})`，前端按 cycle 攒成表格。不需要任何电路建模。

## C.3 换成 Web 前端，架构上要怎么改

先说清 Ripes 的**真实结构**（这决定了它能不能改）【实测 + 推测】：
- Ripes 的处理器**不是"模拟器 + 事后画图"**，而是**用 VSRTL 元件搭出来的电路**（`rv5s.h` 460 行里全是 `vsrtl::core::DFF`、`Mux`、`ALU` 之类的元件接线）。
- 好处：可视化零成本——图就是网表，值就是端口值；还能做"回退一个周期"（`isReversible`）。
- 坏处：**强耦合 Qt + VSRTL**，`processorhandler.h` 直接吃 `vsrtl::VSRTLWidget*`。**无法在浏览器里跑**。

如果你想要 Web 前端【推测，但基于上述依赖关系】：

```
方案 1（不推荐）：把 VSRTL 也搬过去 → 等于用 TS 重写一个 RTL 仿真器，项目范围爆炸
方案 2（推荐）：模拟器（C/C++/Rust）→ Emscripten/wasm-bindgen → JS → 前端只做"渲染快照"
方案 3（最省事）：模拟器保持原生进程，前端用 WebSocket 收 JSON 快照
```
Ripes 自己留了后门：`src/cli/` 说明**核心可以无 GUI 跑**——你做 Web 化时，照着"把 GUI 从核心剥出去"这条缝切就行。

现成的两个 Web 化先例可以直接看：
- rv32emu 自己的 WASM 构建：<https://github.com/sysprog21/rv32emu/blob/master/docs/wasm.md>（Emscripten，依赖 tail-call 特性，Chrome≥112 / Firefox≥121 / Safari≥18.2）
- rvemu 的 wasm 包：`lib/rvemu-wasm`（`Cargo.toml` 里 `crate-type = ["cdylib","rlib"]`，同一个核心既出 CLI 又出 wasm）

## C.4 哪些可视化设计值得借鉴

1. **流水线时空图**（横轴 cycle、纵轴指令，用颜色标段）—— 这是 Ripes 最有教学价值的图，你的演示 PPT 里放一张就够打动人。数据只需 `{cycle, pc, stage}`。
2. **"每条指令现在在哪个段"**（`instructionmodel.cpp` 的做法）：在反汇编列表里给当前指令的所属段加高亮，比单独一张图更直观。
3. **电路图可点元件看值**：你不需要画电路，但可以**点寄存器/CSR 看该值的来源**（谁最后写的）——这是同一个"可解释性"设计思路，成本低得多。
4. **表模型分页/虚拟化**（`memorymodel.cpp` / `registermodel.cpp` 用 `QAbstractTableModel`）：Web 里对应"虚拟滚动列表"，内存视图只渲染可见窗口。
5. **可回退**（`VSRTL::isReversible`）：你这层做不了完整回退，但可以做"最近 N 步的状态环形缓冲"（每步只存变化的那几个寄存器），实现"单步后退"——项目里这是个亮点，成本 100 行以内【推测】。

**CSR 的组织方式（`csr.rs`，354 行）——这个抽象值得直接学**：
```rust
pub type CsrAddress = u16;
pub type CsrFieldRange = RangeInclusive<usize>;   // 位域 = 一个区间
pub const CSR_SIZE: usize = 4096;                 // 12 位地址空间

const MSTATUS: CsrAddress = 0x300;   // 一个 CSR 一个命名常量，按特权级分组注释
const MEPC:    CsrAddress = 0x341;
// 读：按区间取位；写：按区间置位
fn get_field(&self, range: CsrFieldRange) -> u64
```
对比 mini-rv32ima 的裸字段 `uint32_t mstatus`，**"CSR = 地址 + 具名位域区间"是更可维护的表示**；你写可视化界面时，能直接把位域名和值一起显示出来（导师会问"mstatus 第 3 位是什么"）。

**异常的组织方式（`exception.rs`，214 行）——结构极清晰**：
```rust
pub enum Exception {                       // 同步异常：带参数的那种把参数塞进变体
    InstructionAddressMisaligned,
    IllegalInstruction(u64),
    LoadAddressMisaligned,
    EnvironmentCallFromUMode, EnvironmentCallFromSMode, EnvironmentCallFromMMode,
    InstructionPageFault(u64), LoadPageFault(u64), StoreAMOPageFault(u64),
}
pub enum Trap { Contained, ... }           // 委托给 S 模式用
```
处理时按**当前特权级**选 tvec：U/S 模式 → `stvec` 并写 `sepc/scause/stval`；M 模式 → `mtvec` 并写 `mepc/mcause/mtval`。
`src/interrupt.rs`（151 行）单独放中断（mip/mie、STIP/MTIP、PLIC 聚合），与异常分开。

**这一层（CSR 位域 + 异常枚举 + 按模式选 tvec + 中断独立文件）建议你几乎照结构实现**——它恰好覆盖你"特权级/CSR/异常"整个阶段，而且 214 + 151 + 354 = **719 行**，在你预算内。

## D.4 关于 "riscv-rust" 的一处更正

【实测】`https://github.com/riscv-rust/riscv-rust` **返回 404，不存在**。GitHub 上 `riscv-rust` 这个组织是**嵌入式 Rust 生态**（`riscv-rt`、`riscv-rust-quickstart`、`longan-nano` 等，都是跑在真实芯片上的板级支持包），里面没有模拟器。

你说的多半是 **`takahirox/riscv-rust`**：<https://github.com/takahirox/riscv-rust>
License **MIT**（`Copyright (c) 2020 Takahiro`），698 star，自述 "RISC-V processor emulator written in Rust+WASM"。

它的结构【实测】：`src/cpu.rs` **3,780** / `src/mmu.rs` 865（Sv39 页表 + TLB）/ `src/elf_analyzer.rs` 641 / `src/lib.rs` 333（对外 API）/ `src/memory.rs` 157 / `terminal.rs` 37；顶层另有 `cli/` 和 `wasm/` 两个前端。

**定位**：它是 RV64GC + Sv39 + 能跑 Linux 的完整实现，比 rvemu 更大。对你的价值：
- `mmu.rs`（865 行）是"**Sv32/Sv39 页表遍历 + TLB + 权限检查**"的清晰范本——你要做的是把 39 位/Sv39 改成 32 位/Sv32（两级页表变两级、PTE 10+10+12 位）。
- `elf_analyzer.rs`（641 行）是"ELF 解析 + 段加载"的完整参考。
- `lib.rs` 的对外 API 是"核心/前端分离"的又一个样板（和 rvemu 一样：同一核心，CLI + WASM 双前端）。

**结论**：Rust 系（rvemu / rvemu-for-book / takahirox）三者共同示范了同一个架构主张——**核心库 + 薄前端（CLI/WASM）+ 状态导出**。这正是你"模拟器 + 可视化调试界面"该有的形状。

**砍完后**：必读清单 2,405 行里，`proc.c`(602) 可压到 ~350（去掉 fork/wait 的页表复制细节先做简版）、`vm.c`(430) 可压到 ~300（去掉 `uvmcopy` 的 COW 预留）；再加你自己重写的 UART 输出（~40 行）与 init 装载（~60 行）——**「迷你内核」这块落在 2,000 行上下**，占你 7,300 行预算的 27%，是合理的。

## E.4 两个"降低难度"的设计取舍【推测/建议，非实测】

1. **可以不用 trampoline**。xv6 的 `TRAMPOLINE` 技巧（同一物理页同时映射到用户页表最高地址和内核页表，用于在切 `satp` 的瞬间还有代码可执行）是为了"纯 S 模式内核 + 无 M 模式固件"。如果你把内核的 trap 入口留在 **M 模式**（像 OpenSBI 那样），M 模式不受 `satp` 影响，就可以在 M 模式里安全地切换 `satp` 再 `mret` 回 U 模式，省掉 trampoline 和它的 134 行汇编。代价：M 模式与 S 模式两套 trap 入口。
2. **`fork()` 可以晚做**。先做 `exec` + `sbrk` + `exit`，能跑"单个用户程序 + 系统调用 + 页错误"就能演示；`fork` 涉及 `uvmcopy` 逐页复制，是调试最痛的一段。
