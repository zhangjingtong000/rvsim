# RVSIM-AIOS：面向 AI 消费者的 OS 接口设计与实现

## 0. 一句话

> 传统 OS 的真相是「现在是什么」；本设计把真相改为「发生过什么」，状态是可重建的投影，AI 是消费者，人通过事件流验证 AI。

---

## 1. 问题

### 1.1 现有 OS 的四个结构性假设

| 假设 | 表现 | 对 AI 的后果 |
|---|---|---|
| 命令式 | `mmap` 要你算好偏移和标志 | 必须理解实现细节 |
| 不可发现 | 能力没有清单，靠文档和试错 | 不知道能做什么 |
| 不可逆 | 没有预演，没有快照 | 试错即破坏 |
| 错误贫乏 | `EACCES` 一个整数 | 失败了不知道为什么 |

四个假设指向同一件事：**OS 假设操作者知道自己在做什么。** AI 不知道，而且会犯错。

### 1.2 一个必须澄清的边界

「完整可操控」在**真实硬件**上不可达，原因是六类原理性障碍（详见 §3.2）：硬件黑盒、微架构状态、观察扰动、已提交的外部副作用、语义不可判定、机密计算设计拒绝。

但在**模拟器**上，这六类障碍大部分消解——模拟器就是系统的全部，没有「边界之外」。

**因此，本设计的研究载体必须是模拟器。这不是退让，是唯一能命题成立的环境。**

## 2. 证据基础

### 2.1 瓶颈不是权限，是理解

| 基准 | 人类 | 最佳 agent |
|---|---|---|
| OSWorld | 72.36% | 12.24% |
| Windows Agent Arena | 74.5% | 19.5% |

两个基准中 agent 都拥有完整桌面控制权，仍然只有 12–20%。论文归因：**GUI grounding and operational knowledge**。

### 2.2 接口表示是数量级的变量，但不是单调规律

**正向证据：**
- SWE-agent 消融：裸 shell 11.0% → 专用 ACI 18.0%
- AgentOccam：仅对齐观察/动作空间，WebArena +26.6 绝对点（+161%）

**反向证据：**
- 「Is Bash All You Need?」（Microsoft, 2026）：60 个 typed tools **44.9%** vs 只用 bash **69.4%**；把 typed tools 叠加到 bash 上**无可测增益**
- 迭代搜索 12.0% < 无搜索 15.7%；整文件 12.7% < 100 行窗口 18.0%
- RAG-MCP：全部 11100 个能力描述 → 选择准确率 13.62%；检索 top-1 → 43.13%
- More Skills Worse Agents：202 个 skill 使通过率降 21%，**68% 的下降来自选错**，上下文过长效应统计上为零

**关键区分：** 正向实验是「在宽接口之上加抽象」，反向实验是「用窄接口替换宽接口」。

> **加抽象 ≠ 删能力。**

### 2.3 空白

子代理独立核查后明确：**没有任何研究**把操作系统状态（进程表/文件系统/网络）建模成可枚举带语义对象，暴露给 agent 并测量效果。

**这既是对该观点的最大空白，也是最值得做的一组实验。**

## 3. 核心决定：事件是真相

```
        事件日志（append-only，不可篡改）
                 ↓ 投影
        当前状态（进程表 / 页表 / 文件树）
                 ↓ 渲染
        人类可读视图
```

传统 OS 反过来：状态是真相，日志是副产物。**这个颠倒派生出全部目标性质：**

| 性质 | 来源 |
|---|---|
| 可审计 | 每条状态变化都有来源与 actor |
| 可回放 | 给定日志可从任意点重建状态 |
| 可回滚 | 回滚 = 重放到某个 seq，无需深拷贝 |
| 可断言 | 断言可作用于事件流 |
| 可解释 | 「为什么变成这样」直接可答 |

**注意：快照恢复的是状态，不是历史。** 事件流 append-only，回滚本身也要记一条事件——否则审计失真（系统看起来从没离开过那个状态，而实际上它被回滚过）。

## 4. 三层模型

```
第 3 层  推荐路径 / 快捷意图 / 友好默认值     ← 可以裁剪
第 2 层  能力清单 / 语义化命名                ← 可发现
第 1 层  完整可操控性                          ← 不裁剪
```

Unix 本来就这么干：内核 syscall 全集完整，shell 只给裁剪过的便利命令。**底层完整，上层友好，两者不冲突。**

**关键：接口层是「目录」，不是「门」。** 若接口层是唯一入口，则「底层完整」是假的。

---

## 5. 设计原则

### 关于真相

- **P1** 事件是真相，状态是投影
- **P2** 事件必须带 actor（谁做的）
- **P3** 事件应用必须确定性（否则不可重放）

### 关于接口

- **P4** 单一权威接口，所有客户端平等
- **P5** 能力清单由内核生成，不由应用注册（应用注册的清单会撒谎）
- **P6** 默认值必须是 AI 友好的那个（因为 AI 常不读文档、不传参数）

### 关于操作

- **P7** 预演与提交分离（plan / apply 共享同一份计划）
- **P8** 破坏性操作标注 `irreversible` 且可预演

### 关于失败

- **P9** 失败必须结构化，绝不静默（静默失败比报错危险一个数量级）

## 6. 已实现

### 6.1 能力清单（P5）

```
rvsh> manifest
{"manifest":1,"caps":15}
{"cap":"run","args":"prog=hello|fork|badptr","irreversible":false,"desc":"装载程序并调度三个进程"}
...
```

**逐行合法 JSON**，由内核生成。

### 6.2 事件日志（P1、P2）

```
rvsh> log
seq actor type arg0 arg1 result code
1 0 spawn 0x80400000 0x80410000 0 code=0
4 0 ecall 0x80000000 0x00000040 -1 code=1
6 0 ecall 0x80410fe0 0x00000001 1 code=0
```

`code` 字段回答「为什么被拒」，而不只是「被拒了」。

### 6.3 断言（P9）

**状态断言：**
```
rvsh> assert spawn=3
{"assert":"spawn","want":3,"got":3,"ok":true}
rvsh> assert foo=1
{"ok":false,"why":"未知断言键"}
```

**产物断言**（验证「输出里有没有出现某内容」）：
```
rvsh> assert uart=rvsh>
{"assert":"uart","want":"rvsh>","ok":true}
```

AI 不必自己解析事件流或翻输出：内核直接回答「是不是这样」。

**实现要点：** 检查产物时必须排除当前命令的回显，否则 `assert uart=rvsh>` 会匹配到自己。因此 `g_cmd_mark` 在命令第一个字符到达前记录，只在它之前的范围内查找。

### 6.4 统一状态入口

```
rvsh> status
{"status":{"nproc":3,"events":3,"plans":0,"snaps":0}}
```

一次调用拿到全貌，AI 不必分别调 ps / log / plans / snaps 再自己拼。

### 6.5 预演与提交（P7、P8）

```
rvsh> plan run badptr
{"plan":1,"intent":"run","prog":"badptr","will":"spawn 3 procs","irreversible":false}
rvsh> plans
{"plans":[{"id":1,"intent":"run","prog":"badptr"}]}
rvsh> apply 1
{"apply":true,"plan":1}
```

### 6.6 快照与回滚

```
rvsh> snapshot
{"snapshot":1}
rvsh> restore 1
{"restore":1,"ok":true}
```

回滚会追加一条 `restore` 事件，使历史保持完整。

### 6.7 完整命令集

`help` `status` `manifest` `ps` `run` `reset` `mem` `uptime` `log` `assert` `plan` `plans` `apply` `snapshot` `snaps` `restore` `tail`

## 7. 端到端验证

一个**不知道 OS 有什么**的客户端，只靠 manifest 发现能力，走完整个闭环：

```
[1] manifest 可解析          (15 项)
[2] 所需元能力齐备            (6 项)
[3] run 参数可枚举            (hello/fork/badptr)
[4] 能创建快照                (id=1)
[5] 初始状态可断言            nproc=3 ok
[6] 能生成计划                prog=badptr
[7] 能执行计划                plan=1
[8] 执行后状态可断言          nproc=0, spawn=3 ok
[9] 能回滚                    id=1
[10] 回滚后状态复原           nproc=3 ok
[11] 回滚本身被记录           restore=1 ok

11/11 通过
```

**关键：第 3 步和第 11 步没有任何硬编码**——程序名是 manifest 告诉它的，结果对不对是事件流告诉它的。

## 9. 边界与风险

### 9.1 已知边界

- 目标是**可证明的完整**：在声明的能力集内完整。
- 确定性是硬要求：时钟虚拟化、随机数种子化、设备可重放。
- 不追求性能。教学与验证优先。

### 9.2 风险

| 风险 | 应对 |
|---|---|
| 被质疑「这不是 OS」 | 立论：重造的是契约，不是内核 |
| 实证可能证明无价值 | 负面结果同样写入论文 |
| 创新性被高估 | 承认 MCP/声明式/事件溯源均为已有概念，贡献在组合与验证 |
| 评分自评偏差 | 以 A/B 对照实验为准，不以自评为准 |

### 9.3 必须区分的两类原因

**技术限制** vs **产品/商业决策**。把商业决策误诊为技术限制，会导致错误的技术路线。

## 10. 下一步

1. **A/B 对照实验**：同一完整底层，A 组裸接口 / B 组分层接口（manifest + 语义名 + assert）。控制变量只改暴露方式。
2. **测量**：任务成功率（每任务 N 次）、步数、错误恢复率、token 消耗。
3. **可变条件**：是否给 manifest、是否给 assert、是否给 plan。

目标不是证明「我们的设计更好」，而是找出**能力集规模与成功率之间的关系**——这是文献空白。

## 11. 相关研究与定位

### 11.1 三条路线，以及本项目的选择

| 路线 | 代表 | 代价 | 结果 |
|---|---|---|---|
| 重写应用内核 | Reor、Void | 极高 | 均已归档 |
| **加状态契约层** | **CLI-Anything（58.3k stars）** | 中等 | **采用最广** |
| 造新品类 | AgentMail、Browserbase | 高 | 早期 |

> **重写不是胜负手，显式状态 + 可验证产物才是。**

本项目选第二条：不重写内核，在既有 RV32 内核上加事件流、能力清单、断言、预演、回滚。

### 11.2 一个必须承认的市场现实

Forrester（2026-07）：仅 8% 常用 AI 浏览器、61% 从不用、19% 愿为主浏览器换 AI 功能。Atlas 已退休，Arc 于 2026-12-22 关闭。

**含义：** 面向终端用户的「AI 原生重写」风险极高。本项目的消费者不是换软件的用户，而是写程序的人与 agent——但这不改变「重写整机应用」的高风险判断。

### 11.3 度量方法（A/B 实验的依据）

《Beyond Task Completion》（arXiv 2610.05047，2026-10）给出可操控性度量的直接框架：

- **Agent-as-a-User**：agent 充当用户完成任务
- **Agent-KLM**：度量**解释成本**与**操作成本**，不只看成功率
- **TUINaut**：轨迹 + **actor-independent oracle**（不依赖操作者的断言）

结论：总成功率掩盖任务差异，**成本排序才相关**。

**限制**：仅覆盖 TUI（15 界面 / 84 任务），未覆盖 OS 层——这是本项目的空间。

本设计的 `assert` 与其中的 actor-independent oracle 思路一致。

### 11.4 一个应当警惕的数字

OSWorld-MCP：接入 MCP 后 o3 从 8.3% → 20.4%，但**最强模型的工具调用率仅 36.3%**。

**含义：** 把能力摆到 AI 面前，它也只有约三分之一的时候能用对。`manifest` 做出来只是第一步，**能否被正确使用是另一回事**——这正是 A/B 实验要测的。

---

## 11. 立论

> 传统 OS 的接口是为「人写程序」设计的：命令式、状态导向、不可回滚。
> 本文以模拟器为载体，实现一种面向 AI 消费者的 OS 接口模型：事件为真相、能力自描述、意图式调用、预演与提交分离、失败结构化、状态可回滚。
> 并通过一个不知情的客户端验证其可用性，为后续对照实验提供基线。

一句话：

> **不是让 AI 能操控 OS 的全部，而是让 OS 的每个能力都以 AI 能正确选择的形式存在。**
