# RVSIM-AIOS：面向 AI 消费者的 OS 接口设计

## 0. 摘要

传统操作系统的消费者是「人」和「人写的程序」，因此它的接口是为「知道自己在做什么」的操作者设计的：命令式、状态导向、不可回滚、错误信息贫乏。

AI 是第三种消费者，它的特征完全不同：它不知道细节、会犯错、需要自我验证。

本设计把内核的真相从「当前状态」改为「发生过什么」，并据此派生出一组接口性质。状态成为事件流的投影，回滚成为重放，审计成为一等能力。

---

## 1. 问题陈述

### 1.1 现有 OS 的四个结构性假设

| 假设 | 表现 | 对 AI 的后果 |
|---|---|---|
| 命令式 | `mmap` 要你算好偏移和标志 | 必须理解实现细节才能调用 |
| 不可发现 | 能力没有清单，靠文档和试错 | 无法知道能做什么 |
| 不可逆 | 没有预演，没有快照 | 试错即破坏 |
| 错误贫乏 | `EACCES` 一个整数 | 失败后没有信息 |

这四个假设都指向同一件事：**OS 假设操作者知道自己在做什么。**

### 1.2 非目标

本设计**不**追求「AI 能操控 OS 的一切」。已有数据表明更大能力集未必更好（见 §2.3）。

## 2. 证据基础

### 2.1 瓶颈不是权限，是理解

| 基准 | 人类 | 最佳 agent |
|---|---|---|
| OSWorld | 72.36% | 12.24% |
| Windows Agent Arena | 74.5% | 19.5% |

两个基准中 agent 都拥有完整桌面控制权（能截屏、点击、输入），仍然只有 12–20%。论文归因为「GUI grounding and operational knowledge」。

### 2.2 接口表示是数量级的变量

| 实验 | 结果 |
|---|---|
| SWE-agent 消融（SWE-bench Lite，GPT-4 Turbo） | 裸 shell 11.0% → 专用 ACI 18.0%（相对 +64%） |
| AgentOccam（仅对齐观察/动作空间） | WebArena +26.6 绝对点（+161%） |

同一模型、同一任务，变量只有接口形态。

### 2.3 更多能力反而更差

```
迭代式搜索   12.0%  <  无搜索     15.7%
全文件给入   12.7%  <  100 行窗口 18.0%
完整历史     15.0%  <  最近 5 条   18.0%
```

### 2.4 接口设计不能保证可靠

- τ-bench：结构化 API 下 `pass^8` < 25%
- ToolEmu：最安全 agent 仍有 23.9% 高风险失败率
- TheAgentCompany：最强 agent 自主完成 30%

**结论：接口是必要条件，不是充分条件。**

### 2.5 可编程性强的软件的共性（8 正例 / 5 反例调研）

1. 单一权威接口，GUI 只是客户端
2. 输出格式为脚本设计且承诺稳定
3. 退出码是契约
4. 默认非交互，交互需显式开关
5. 预演与提交分离
6. 状态可快照、可回滚
7. 错误是可编程消费的数据

**反例的根因几乎都是默认值**：OpenSSH 默认强制交互（`BatchMode` 关闭）、MySQL 默认人类表格（`--batch` 才结构化）、psql 默认遇错继续（`ON_ERROR_STOP` 默认关）。

> AI 经常不读文档、不传参数、直接用默认行为。**默认值就是契约。**

### 2.6 最危险的失败是静默失败

openpyxl 读公式单元格返回 `None` 且无错误信号。不报错、不警告，给出错的值。

**静默失败使 AI 无法察觉自己错了，比报错危险一个数量级。**

## 3. 核心决定：事件是真相

```
        事件日志（append-only，不可篡改）
                 ↓ 投影
        当前状态（进程表 / 页表 / 文件树）
                 ↓ 渲染
        人类可读视图
```

传统 OS 反过来：状态是真相，日志是副产物。**这一个颠倒派生出全部目标性质：**

| 性质 | 来源 |
|---|---|
| 可审计 | 每条状态变化都有来源与 actor |
| 可回放 | 给定日志可从任意点重建状态 |
| 可回滚 | 回滚 = 重放到某个 seq，无需深拷贝 |
| 可断言 | 断言可作用于事件流，不只看终态 |
| 可解释 | 「为什么变成这样」直接可答 |

**回滚用重放而非快照，是最大的实现简化**：省掉页表深拷贝与进程上下文深拷贝这两处最易出 bug 的代码。

## 4. 设计原则

### 关于真相

**P1 事件是真相，状态是投影。**
任何状态变化必须先成为事件。

**P2 事件必须带 actor。**
没有 actor，能看到「进程被杀了」，但不知道「谁杀的」。审计的关键字段。

**P3 事件应用必须确定性。**
相同事件序列产生相同状态。否则不可重放。

### 关于接口

**P4 单一权威接口。**
内核是唯一权威。shell、Web 前端、AI 客户端地位平等，不存在「只有某个界面能做」的操作。

**P5 能力清单由内核生成。**
应用注册的清单会撒谎，内核生成的不会。启动时输出。

**P6 默认值必须是 AI 友好的那个。**
不是提供开关，而是把默认路径设为非交互、结构化、遇错即停。

### 关于操作

**P7 预演与提交分离。**
`intent → plan（生成事件但不追加）→ 审阅 → apply（追加并应用）`。保证审阅的就是执行的。

**P8 破坏性操作必须标注且可预演。**
`irreversible: true`，且 plan 阶段就能看到其效果。

### 关于失败

**P9 失败必须结构化，绝不静默。**
返回 code、位置、原因、可操作建议、以及可回溯的 `audit_seq`。

## 5. 架构

```
┌──────────────────────────────────────────┐
│ 渲染层   人类可读视图 / JSON 视图          │
├──────────────────────────────────────────┤
│ 接口层   intent / plan / apply / assert  │
│          manifest（能力清单）             │
├──────────────────────────────────────────┤
│ 计划层   plan 缓冲（未提交的事件序列）     │
├──────────────────────────────────────────┤
│ 内核     事件日志（真相） → 状态投影       │
│          调度 / 页表 / 设备 / UART        │
└──────────────────────────────────────────┘
```

四层职责单一，自上而下只读，自下而上只发事件。

## 6. 接口规范

### 6.1 事件

```c
struct evt {
    u32 seq;        /* 单调递增，不可回退 */
    u64 ts;         /* 虚拟时钟，非真实时间，保证可重放 */
    u32 actor;      /* 发起者：进程号 / 会话号 */
    u16 type;       /* EVT_PROC_SPAWN / EVT_PROC_EXIT / ... */
    u32 arg[3];
    s32 result;     /* 0 成功；负数错误码 */
};
```

### 6.2 能力清单（manifest）

内核启动时输出，AI 读它即知能力边界：

```json
{"cap":"spawn",
 "args":{"prog":{"enum":["hello","fork","badptr"]}},
 "ret":"pid",
 "irreversible":false,
 "pre":["nproc < NPROC"],
 "errs":["E_NPROC_LIMIT","E_BAD_PROG"]}
```

### 6.3 三段式调用

```json
{"intent":"spawn","prog":"hello"}        → {"plan_id":7,"events":[...]}
{"apply":{"plan_id":7}}                  → {"ok":true,"seq_range":[120,124]}
{"assert":"uart =~ /rvsh>/"}             → {"ok":true,"audit_seq":124}
```

### 6.4 结构化失败

```json
{"ok":false,
 "code":"E_BAD_PTR",
 "at":"write(buf=0x90000000,len=8)",
 "why":"buf 不在用户地址区间 [0x80400000,0x80800000)",
 "fix":"使用栈或堆上的地址",
 "audit_seq":1234}
```

## 7. 实验设计

### 7.1 假设

> 在同一个 OS 上，把能力裁剪成有限、语义化、带后果说明的集合，agent 的任务成功率高于开放完整 shell；继续扩大能力集会降低成功率。

### 7.2 分组

| 组 | 接口 |
|---|---|
| A | 完整 shell，全部命令，errno 风格错误 |
| B | 6–8 个意图 + manifest + 结构化错误 + irreversible 标注 + plan/apply |

### 7.3 任务

自然语言描述，覆盖：进程管理、内存越界、并发协作、错误恢复。

### 7.4 指标

- 任务成功率（每任务 N 次，参考 τ-bench 的 `pass^8`）
- 完成步数
- 错误恢复率
- token 消耗
- 越界操作次数（审计发现）

### 7.5 预期结果与价值

无论 A/B 哪个更好都是有效结论。若能画出「能力集规模 vs 成功率」曲线并找到拐点，则是现有文献未做的贡献。

## 8. 边界与风险

### 8.1 已知边界

- 目标是**可证明的完整**，不是「一切皆可操控」：在声明的能力集内完整。
- 确定性是硬要求，这会约束设计（时钟虚拟化、随机数种子化、设备可重放）。
- 不追求性能。教学与验证优先。

### 8.2 风险

| 风险 | 应对 |
|---|---|
| 被质疑「这不是 OS」 | 明确立论：重造的是契约，不是内核 |
| 创新性被高估 | 承认 MCP / 声明式 / 事件溯源均为已有概念，贡献在组合与验证 |
| 实验可能得出负面结果 | 负面结果同样写入论文 |
| 快照/重放做不完 | 降级为进程级 checkpoint |

### 8.3 必须区分的两类原因

技术限制 vs 产品/商业决策。把商业决策误诊为技术限制，会导致错误的技术路线。

---

## 9. 实施顺序

优先级按「是否直接影响 AI 成功率」排序，而非按理论优雅度：

1. **事件结构 + actor**（底座，最小可跑）
2. **plan / apply 两段式**（直接改变成功率）
3. **定默认值**：非交互、结构化输出、遇错即停
4. **能力清单 manifest**
5. **replay / assert**
6. **A/B 实验与测量**

前三步完成后即可开始实验；后两步为补强。

---

## 10. 立论

> 传统 OS 的接口是为「人写程序」设计的：命令式、状态导向、不可回滚。
> 本文提出并实现一种面向 AI 消费者的 OS 接口模型：事件为真相、意图式调用、预演与提交分离、失败结构化、能力自描述。
> 并在 RV32 模拟器上完成实现，通过 A/B 对照验证其对 agent 任务成功率的影响。

一句话：

> **不是让 AI 能操控 OS 的全部，而是让 OS 的每个能力都以 AI 能正确选择的形式存在。**
