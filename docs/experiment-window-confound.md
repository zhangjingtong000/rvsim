# 实验补充：上下文窗口是混杂变量（已修正）

**日期**：2026-11-05
**任务**：需要历史的三问（真值 `exit=9 oob=18 first=0`）

---

## 1. 发现过程

第一轮用 SiliconFlow 的 `deepseek-ai/DeepSeek-V4.1-Flash` 跑 B 组，**失败**：

```
manifest → run prog=badptr(错) → plan/apply ×3 → log → answer={"exit":9,"oob":9,...}
```

它读了 `log`，却数出 `oob=9`（真值 18）。

**原因不是模型能力，是我的 prompt 只给最近 2000 字符**——
而 39 条事件的 `log` 输出约 2000 字符，**恰好卡在边界**，模型没看全却照样给出数字。

把窗口放宽到 4000 后重跑：

```
steps=9 tokens=27567 answer={"exit":9,"oob":18,"first":0}  -> 正确
```

**同一模型、同一任务、同一个 API，唯一变量是窗口大小。**

---

## 2. 这说明了什么

### 2.1 `log` 的输出长度是硬约束

事件流是「完整真相」，但**一次性倾倒给模型时，真相会被窗口截断**。
被截断的真相比没有真相更危险——**模型会基于残缺数据自信地给出错误答案**。

### 2.2 这正是 `assert` 存在的理由

对比两种拿到 `oob` 的方式：

| 方式 | 代价 | 风险 |
|---|---|---|
| 读 `log` 自己数 | O(事件数) token | 窗口截断即数错 |
| `assert oob=18` | 一次往返 | 无 |

官方版 `deepseek-flash` 那 3 次成功，都是**用 `assert` 拿到的**；
这次失败的那一轮，是**读 `log` 自己数的**。

> **`assert` 的价值不是「更结构化」，是「把 O(n) 的阅读变成 O(1) 的查询」。**

## 3. 修正后的完整数据

| 模型 | 平台 | 窗口 | A 组 | B 组 |
|---|---|---|---|---|
| deepseek-flash | DeepSeek 官方 | 2000 | **0/3** | **3/3** |
| deepseek-v4.1-flash | SiliconFlow | 2000 | — | 0/1（数错） |
| deepseek-v4.1-flash | SiliconFlow | **4000** | — | **1/1（正确）** |
| Qwen3-30B-A3B | SiliconFlow | 2000 | 0/1 | 0/1（读了 log，不会用 assert） |
| GLM-4-9B | SiliconFlow | 2000 | 0/1 | 0/1（完全没用 manifest） |
| Qwen2.5-7B | SiliconFlow | 2000 | 0/1 | 0/1（幻想 Linux 管道） |

---

## 4. 诚实标注

1. **窗口改动发生在实验过程中**，不是预期设计。前面 A 组的 3 次是在 2000 下跑的。
   但 A 组没有 `log`，输出本来就短，窗口对它影响小。
2. **deepseek-v4.1-flash 只有 1 次成功样本**（额度限制）。
3. **小模型（7B/9B/30B-A3B）的失败仍然成立**，且失败方式各不相同，这部分结论不受窗口影响
   （它们连 `manifest` 都不读，或假设了 POSIX）。
4. **平台差异未完全排除**：官方 API 与 SiliconFlow 的采样参数可能不同。

---

## 5. 结论

> **「有事件流」还不够，还要能「低成本地查询事件流」。
> 把 39 条事件倒给模型，它会在窗口边界上数错；
> 给它一个 `assert oob=18`，一次就对。**

这也修正了前面那句结论：

> ~~事件流对需要历史的问题必要~~
> **事件流必要，但必须配合低成本的查询原语（`assert`），否则会被上下文窗口反噬。**
