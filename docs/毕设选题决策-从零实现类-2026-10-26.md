## 1. 为什么是这个方向（画像回顾）

委托人的硬约束（经三轮修正后的最终版本）：

| # | 约束 | 性质 |
|---|---|---|
| 1 | 不做硬件 | 绝对禁止（例外：已有设备） |
| 2 | 不做浅层任务（检测/分类/识别/抽取） | 绝对禁止 |
| 3 | 不能太抽象（评委也要懂） | 绝对禁止 |
| 4 | 数据集必须可得，且不需人工逐片筛选/标注 | 硬约束 |
| 5 | 体量必须讲得完，且初始设计就要有深度路径 | 硬约束 |

优先级（非硬约束）：工程型 > 研究型；完整系统；有深度；具体；有可视化更好；
调参可以接受；负收益可以接受；正收益不是硬约束。

**「从零实现一个系统」这一类之所以最优，是因为它同时绕过 4 和 5**：
不需要数据集（输入是程序生成的或标准测试集），且深度路径由外部规范决定，不靠自己加功能。

## 2. 核心方法论（本轮最重要的产出）

### 2.1 验收合同硬度分级

> **验收硬度几乎完全由「格式/行为是不是别人定好的」决定。**

| 级别 | 形式 | 例子 | 容差 |
|---|---|---|---|
| A+ | **文件自带校验值** | FLAC（STREAMINFO 里的 PCM MD5） | 无 |
| A | **逐字节/逐比特一致** | Git 对象哈希、PNG 逐字节 | 无 |
| A- | **官方测试集逐条断言** | UAX #14 LineBreakTest、c-testsuite | 无 |
| B | **与成熟实现对拍** | SQL 结果集 vs SQLite、合并结果 vs git merge-file | 无/极小 |
| C | **逐像素 + 容差** | SVG vs resvg 期望图 | 需自定 |
| D | **性能指标** | 写放大、延迟、帧率 | 阈值 |
| E | **看图/主观** | 光栅化器、路径追踪 | 无标准 |

**选题原则：落在 A+ 到 B 之间。C 以下不要碰。**

### 2.2 台账：教程密度与验收硬度反相关

实测支撑：

- **有完整教程 → 验收软**：tinyrenderer（[24,460★](https://github.com/ssloy/tinyrenderer)，14 章分步课程，终版约 500 行，README 称学生需 10–20 小时）、[Ray Tracing 三部曲](https://raytracing.github.io/)、[kilo 编辑器](https://github.com/antirez/kilo)（9,197★，<1000 LOC + 分步教程）、[MIT 6.5840 Raft lab](https://pdos.csail.mit.edu/6.824/labs/lab-raft1.html)
- **验收硬 → 无端到端教程**：resvg 逐像素测试集、Unicode 一致性测试、git 哈希对拍

**推论：有教程是好事（可行），也是坏事（显得照抄）。要找的是「有权威规范、有生产级实现可对拍、但没有分步教程也没有极简参考实现」的位置。**

### 2.3 常见程度是独立的一票否决维度

GitHub 仓库检索（`in:name,description`，2026-10-26，噪声大只看量级）：

## 4. 第一名：表格公式引擎 + 依赖图增量重算

### 4.1 三重独立验收判据

这是全部候选里唯一**能不依赖外部 oracle 自证**的题目：

1. **外部对拍**：逐单元格与 Excel / LibreOffice 比对。
   - Excel：[`Application.Calculate`](https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculate)，Windows 原生优势
   - LibreOffice：无头 `calculateAll()`，[现成脚本](https://github.com/anthropics/skills/blob/main/skills/xlsx/scripts/recalc.py)
2. **内部金标准**：**增量重算结果必须与全量重算逐位一致**。零外部依赖、永真，抓的是"算错但碰巧对上"。
3. **过程指标**：**重算单元格数必须等于依赖闭包大小**。防"偷偷全量重算假装增量"——这是本题最核心的可作弊点，而它是可数的。

参考点：salsa 的 [`EventKind`](https://docs.rs/salsa/latest/salsa/enum.EventKind.html) 明确区分 `WillExecute`（真重算）/ `DidValidateMemoizedValue`（验证后复用）/ `DidDiscard`，说明"重算次数可观测可断言"是成熟做法。

### 4.2 为什么它是最优

- **无数据集**：随机工作簿生成器可无限出题
- **Windows 是优势**：这台机器装 Office 就有工业级 oracle
- **可视化天然**：依赖图 + 重算热力图；改一个格子看涟漪扩散，评委一秒理解
- **抗失控极强**：加功能不能提高单元格一致率
- **深度是架构级**：依赖图、拓扑排序、循环检测（`#CIRC!`）、增量传播、错误码传播、区间运算、易变函数处理

### 4.3 必须提前钉死的边界

**三个引擎的公式语义实测有分歧。** [canispreadsheet](https://canispreadsheet.com/guides/) 称在 2,334 个用例中，**272 个用例（135 个函数）** LibreOffice 把微软文档的 `#NUM!`/`#N/A`/`#DIV/0!`/`#REF!` 统一报成 `#VALUE!`。LibreOffice 版本差异真实存在（VSTACK/TEXTSPLIT 直到 25.8.7.3 才可用）。

⇒ 开题第一句必须写：**以哪个引擎、哪个版本为准**。
⇒ 函数集必须书面冻结；动态数组、`INDIRECT`、`OFFSET` 明确不支持。

函数语义参考：[HyperFormula](https://github.com/handsontable/hyperformula)（2,821★，400+ 公式）。

### 4.4 五模块

1. 词法/语法解析（公式 → AST）
2. 依赖图构建与增量维护（区间引用、跨表引用）
3. 求值器（函数库子集、类型与错误码传播）
4. 增量重算调度（脏集传播、拓扑序、循环检测）
5. 可视化与基准（依赖图、重算热力图、重算计数器）

### 4.5 阶段门

| 阶段 | 交付 | 验收 |
|---|---|---|
| G1 | 解析 + 单格求值 | 200 个公式用例，AST 与求值结果正确 |
| G2 | 依赖图 + 全量重算 | 与 LibreOffice 逐单元格一致率 ≥ 目标 |
| G3 | 增量重算 | **增量 ≡ 全量（bit 级）100%** |
| G4 | 重算计数器 | **重算数 == 闭包大小 100%** |
| G5 | 可视化 + 性能 | 10 万单元格工作簿的重算延迟曲线 |

## 5. 第二名：diff / 三方合并

### 5.1 验收（最不可狡辩）

[`git merge-file` 官方文档](https://git-scm.com/docs/git-merge-file)把语义写死：
- 冲突标记 `<<<<<<<` / `=======` / `>>>>>>>`
- `--diff3` / `--zdiff3` / `--marker-size` / `--diff-algorithm={patience|minimal|histogram|myers}`
- **退出码 = 冲突数**（>127 截断为 127，干净为 0）

⇒ **逐字节 + 退出码双重判定。** GNU diff `-u` 输出确定。

### 5.2 优势与短板

优势：全 GitHub `three-way merge` 仅 **12** 个仓库；三月可行性最高；Windows 零摩擦（Git for Windows 自带 oracle）。

短板：**体量偏小**，必须主动加料：
- 三种 diff 算法（myers / patience / histogram）
- 树级 diff + 重命名检测（对拍 `git diff --raw`）
- `--ours` / `--theirs` / `--union`
- 前端可视化合并 UI
- 10 万行 / 1MB 性能曲线

注意：**固定 LF 处理**，否则 CRLF 会造成假失败。

### 5.3 参照物

diffutils `tests/` 19 个条目；git 仓库 `t/` 有 **2,017 个测试脚本**。

## 6. 第三、四名（备选）

### FLAC 解码器（验收最硬，A+）

- [RFC 9639 §8.2](https://www.rfc-editor.org/rfc/rfc9639.html#appendix-D)：STREAMINFO 内含 u(128) **原始 PCM 的 MD5** → 解码器可自证
- [flac-test-files](https://github.com/ietf-wg-cellar/flac-test-files)（CC0）：`subset/`（数十文件）、`uncommon/`（11）、`faulty/`（11 负例，要求不崩溃）
- 体量锚点：[claxon](https://github.com/ruuda/claxon)（Rust）≈ 143KB / 7 文件 / **约 4,000 行**
- Oracle：Xiph 官方 Windows `flac.exe`
- 风险：**细节密集**（escaped partition、wasted bits、negative LPC shift，差一位就全错）。排期要留整两周专做"subset 全绿"，不要放在最后一周
- 建议做成"解码器 + 简化编码器 + 帧结构可视化前端"

### SVG 渲染器（可视化最强，验收 C 级）

- 真值：[resvg-test-suite](https://github.com/linebender/resvg-test-suite)，每个 `.svg` 配同名 `.png`（实测 `tests/shapes/path` 下 **114 个文件成对**）
- 7 大类天然阶段门：shapes / painting / paint-servers / structure / masking / filters / text
- 无分步教程 → 照抄风险低
- 风险：抗锯齿"正确"无唯一定义（resvg 也可能与浏览器不同）→ 容差必须自己标定并写进报告；filters 三个月内应放弃；text 只做已转路径

## 7. 明确排除清单及理由

| 候选 | 排除理由 |
|---|---|
| **LSM 存储引擎** | [Mini-LSM](https://skyzh.github.io/mini-lsm/) 是完整三周课程（每周 7 章、每章 2–3h），**自带测试套件 + 参考解 + 逐章 checkpoint** → 同质化最严重；且磁盘格式自定，验收只能验行为 |
| **编译器 / 解释器** | chibicc 11,952★、Crafting Interpreters 11,119★、有全国赛事；`lox interpreter` 3,563 仓库 → 最饱和 |
| **路径追踪渲染器** | Ray Tracing 三部曲逐行给代码（照抄风险最高）× 验收只能看图（最软）→ 性价比最差 |
| **Raft** | MIT lab 有官方 tester，网上成千上万公开实现；tester 是 sh 脚本，Windows 摩擦最大 |
| **FLAC 极简实现路线** | 存在"500 行 Go 写 FLAC 编码器"这类极简实现（[goflac](https://github.com/schollz/goflac)、[nayuki simple-flac](https://github.com/nayuki/Nayuki-web-published-code)、[flac-py](https://github.com/turlando/flac-py)）→ 体量会被压缩、照抄风险上升。**必须做完整解码器（4000 行量级）而非子集** |
| **DEFLATE 压缩器** | zlib 自带 `contrib/puff/puff.c`（37,891 字节 ≈ 1000 行完整 inflate）→ 撞"抄参考实现"风险最高 |
| **JPEG 编解码** | 有损格式，只能 PSNR / 像素差容差对比 → 软验收 |
| **时序数据库 TSDB** | 未找到权威分步教程，验收只能自建测试 + 压缩率 → 演示难证"对了" |
| **P2P 软件光栅化器** | tinyrenderer 14 章课程 + 验收只能看图 |
| **字体栅格化** | 体量偏小（1.5–2.5k）；完整 hinting 不可做（FreeType `ttinterp.c` 单文件 **187,596 字节**，stb_truetype 至今 `// @TODO implement hinting`） |
| **文本排版引擎** | 验收最硬（[LineBreakTest-18.0.0.txt](https://www.unicode.org/Public/UCD/latest/ucd/auxiliary/LineBreakTest.txt) 19,377 行 + BidiTest）但体量 2.5–4k 且**最易超期**；GSUB/GPOS 全做必死 |
| **容器运行时 / FUSE / 用户态 TCP** | 只能 Linux，委托人在 Windows |
| **终端模拟器** | vttest 是 Unix 程序，Windows 需 MSYS2/Cygwin，截图比对需人工判读 |
| **IOCP HTTP 服务器** | 验收偏软（未找到权威 HTTP/1.1 服务端一致性测试套件，h2spec 只测 HTTP/2）；"从零"边界模糊 |

## 8. 下一步：四个探针（先验证，再承诺）

**目的**：选题本质是在信息不足时做承诺。探针把承诺换成验证，成本 <1 天，但能削掉三个月的不确定性。

| 探针 | 只验证一件事 | 成本 | 淘汰条件 |
|---|---|---|---|
| 表格引擎 | 能否用 LibreOffice 无头重算拿到逐单元格 oracle | 2–3h | 拿不到 → 降级为"只做内部金标准"（仍可行） |
| diff/merge | `git merge-file` 对拍管线能否跑通 | 1h | 跑不通 → 出局 |
| FLAC | `flac.exe -t` + MD5 校验能否闭环 | 1–2h | 闭环不了 → 出局 |
| SVG | resvg 测试集 diff 脚本能否跑出通过率 | 2h | 跑不出 → 出局 |

**探针产出必须是可执行的东西**（一条能跑的命令 + 一个数字），不是结论。

## 9. 方法论教训（写给自己）

**为什么前三轮的推荐会错得这么系统？**

| 我当时的推荐 | 当时理由 | 现在为什么错 |
|---|---|---|
| LSM 排第一 | "验收机械、深度天然" | 没查**参照物密度**（Mini-LSM 三周课程含参考解） |
| 路径追踪进 B 档 | "可视化冲击强" | 没查**照抄风险**（三部曲逐行给代码） |
| 编译器进 B 档 | "测试集硬" | 没查**常见程度**（两本 1 万星的书 + 全国赛事） |
| 把 FLAC 判为"体量不足" | 看到"500 行实现" | 那是**极简子集**实现，完整实现 4000 行 |

**共同错误：只评估了「能不能做对」，没评估「做对了算不算你的」和「别人是不是早就做烂了」。**

**可复用的检查清单**（每次评估选题都过一遍）：
1. 验收合同是什么级别？（A+～E，C 以下不碰）
2. 有没有**完整分步教程**？（有 → 可行性高但演示风险高）
3. 有没有**极简参考实现**？（有 → 体量可能被压缩 + 照抄风险）
4. **常见程度**多少？（GitHub 仓库数量级 + 相关课程/赛事）
5. 体量的下限是多少？（能不能被几百行实现覆盖）
6. 加功能能不能提高验收通过率？（能 → 会失控；不能 → 抗失控）
7. 三个月能到哪一档？（要能交出一个"通过率 X%"的系统，不是半个）
