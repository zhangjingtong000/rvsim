# 桌面操作系统构成调研 · 与 rvsim 现状对照

> 目的：在动手之前先看清楚「一个桌面操作系统到底由什么构成」，逐项对照我们做到哪一步、
> 差距在哪、业界是怎么实现的。不写代码，只做盘点与判断。

## 一、桌面 OS 的标准构成（十二层）

参考来源：政府采购操作系统技术规范、OS.js 架构、Apple HIG / Windows Fluent / GNOME HIG 对照、
bevel-os 与 Arch-Web 等开源实现。

| # | 层 | 职责 | 标准做法 |
|---|---|---|---|
| 1 | 引导 | 固件 → 内核 → 首个用户态进程 | splash / 进度 / 品牌动画 |
| 2 | 会话 | 登录、用户、锁屏 | 登录页、头像、密码框、切换用户 |
| 3 | 合成器 | 把多个窗口的像素合成到屏幕 | GPU 合成、圆角裁剪、阴影、模糊、透明度 |
| 4 | 窗口管理 | 位置/尺寸/层叠/焦点 | 拖动、缩放边界、吸附、分屏、Alt+Tab、多任务视图 |
| 5 | 桌面外壳 | 壁纸、图标、右键菜单 | 图标网格、双击打开、重命名、拖拽摆放 |
| 6 | 任务栏 / Dock | 启动器 + 运行中任务 + 状态区 | 固定与临时项、指示点、通知区（网络/音量/电量/时钟） |
| 7 | 应用启动器 | 开始菜单 / Launchpad | 搜索、分类、最近使用、固定 |
| 8 | 文件管理 | 浏览、增删改、预览 | 图标/列表视图、地址栏、多选、右键菜单、拖拽 |
| 9 | 终端 | 命令行 | 真字体、滚动回看、选中复制、多标签 |
| 10 | 设置 | 外观、账户、网络、显示 | 分区、即时生效 |
| 11 | 通知 / 弹窗 | 系统消息、对话框 | 右上角堆叠、自动消失、可点开 |
| 12 | 应用生态 | 独立应用、包管理 | 从磁盘加载、沙箱、权限 |

## 二、我们现在的真实状态

### 已经有的

| 层 | 我们的实现 | 完成度 |
|---|---|---|
| 引导 | 前端 splash（rvsim 标识 + 滑动进度条），3.5 秒后淡出 | 有，但很简陋，只是加载遮罩 |
| 合成器 | 内核画内容到独立缓冲区，宿主读窗口表用 HTML/CSS 合成 | **架构是对的**，但只有矩形，没有真正的合成层 |
| 窗口管理 | 拖动、聚焦、z 序、最大/最小/关闭、轮廓拖拽 | 基本动作齐了，缺缩放/吸附/分屏/Alt+Tab |
| 桌面外壳 | 只有渐变壁纸，**没有图标** | **缺** |
| 任务栏 | 底部 Dock：启动按钮 + 3 个 chip + 时钟 | 有骨架，chip 点击失效、无通知区 |
| 启动器 | 开始菜单写了 DOM 版，**没弹出来** | **坏** |
| 文件管理 | Files 窗口只读列表（NAME/SIZE） | **只读，不能操作** |
| 终端 | 内核按 8×16 点阵字画到画布，宿主贴图 | **字难看（点阵）、不能选中复制、无滚动** |
| 设置 | 无 | **缺** |
| 通知 | 无 | **缺** |
| 应用生态 | 内核能加载 ELF 并运行（hello/fork/fdtest/badptr） | 有底层能力，但**桌面上没有入口** |

### 内核侧真实能力（这些是真的，不是壳子）

shell 共 30 个命令：`help manifest ps ls ll cat mkdir rm chmod write run run fork snap snaps
snapshot plans replay verify log status mem uptime whoami clear echo settime guide dumpterm reset resume tail`

- 进程管理：spawn、调度、状态（RUN/READY/EXIT）、PC 查看
- 文件系统：RAMFS，16 个槽位，支持目录、权限、属主
- 事件流：13 类事件、16384 容量、可重放/回滚/预演
- ELF 加载：能跑独立程序

**内核的能力比外壳展示出来的多得多。** 问题不在内核，在呈现。

## 三、差距的根因判断

### 1. 字体难看 —— 这是架构决定的，不是调参能解决的

内核对每个字符画 8×16 点阵。点阵字：
- 没有抗锯齿，边缘全是硬块
- 8 像素宽放不下汉字的细节，只能靠 16×16 勉强辨认
- 放大后更糊（`image-rendering: pixelated`）

**任何「调颜色、换字体文件」都改不了这一点。** 要么宿主用真字体渲染文本，要么内核算出抗锯齿的两个问题都绕不开。

### 2. 关掉三个窗口后桌面全空 —— 因为桌面层根本不存在

我们没有「桌面图标」这个概念。窗口是硬编码的三个（terminal/monitor/files），
关掉就没有任何入口能再打开——开始菜单还是坏的。

### 3. 拖动和输入时好时坏 —— 事件转发的单点设计

所有鼠标事件都从 `#desk` 转发给内核（写 MMIO 坐标），
窗口上的 DOM 元素一旦 stopPropagation，拖动和焦点就一起废。
这是**把 DOM 交互和 guest 坐标混在一层**带来的结构性问题。

### 4. 「像不像 OS」—— 我们缺的是外壳的完整度，不是内核

对照第一节的十二层，我们缺 4 层（设置、通知、桌面图标、应用生态入口），
坏了 2 层（开始菜单、文件操作），弱 2 层（终端、任务栏）。

## 四、两条路线的取舍

### 路线 A：内核继续画内容，宿主补外壳
- 优点：改动小，已经做了一半
- 缺点：**字体问题无解**（点阵字），终端永远难看；桌面图标要内核画，仍然丑

### 路线 B：内核只供数据，宿主渲染一切
- 内核暴露：终端字符网格（码点）、进程表、文件表、事件流
- 宿主用 HTML/CSS 渲染：终端（真字体）、表格、图标、菜单
- 优点：字体、图标、交互全部现代化；内核的「真实数据」价值还在
- 缺点：改动大；「OS 自己画像素」这个卖点弱化

### 我的判断

用户要的是「像 Windows 那样」。**只要字体是点阵的，就不可能像。**
所以路线 B 是唯一能满足目标的方向，但它需要一次性重做外壳，不是修补。

## 五、如果走路线 B，需要内核提供的数据接口

| 数据 | 形式 | 现状 |
|---|---|---|
| 终端字符网格 | 80×30 的 u32 码点 + 光标位置 | 已有（g_term），需暴露 |
| 进程表 | 每项 {pid, state, pc, name} | 已有（procs[]），需暴露 |
| 文件表 | 每项 {name, size, type, owner, mode} | 已有（fs_entry），需暴露 |
| 事件流 | 最近 N 条 {seq, type, detail} | 已有，需暴露 |
| 窗口表 | {buf/w/h/x/y/z/focus/visible} | 已有（刚做的 g_win_info） |

**这些数据内核都已经在维护，只是没有以「宿主能直接读」的形式暴露出来。**

## 六、结论

1. 内核能力足够，问题全在呈现层。
2. 点阵字体是「不像 OS」的最大单点原因，且无法通过调参解决。
3. 缺的是外壳完整度：桌面图标、可用的开始菜单、文件操作、设置、通知。
4. 建议走路线 B：内核供数据，宿主渲染界面。这是一次重做，不是修补。
