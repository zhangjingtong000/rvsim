# 实验：破坏性操作（快照与回滚）

**日期**：2026-11-05
**模型**：deepseek-flash（官方 API，temperature=0）
**任务类型**：破坏性操作 —— 能力有无，不是效率高低

---

## 1. 为什么换这个任务

前两个任务都是「计数」，A 组有**碰巧猜对**的可能（虽然实测都猜错了）。
这个任务不一样：**A 组根本没有 `snapshot` / `restore` 命令**，
不存在猜中的可能。

---

## 2. 任务

> 按顺序完成三件事：
> 1. 创建一个当前状态的快照（存档）
> 2. 运行 badptr 演示
> 3. 回滚到刚才那个快照，让系统恢复到存档时的状态
>
> 最终单独一行输出：`ANSWER: snapshot=<编号> restored=<true|false> nproc=<当前进程数>`

## 3. 审计方法（不采信模型自述）

```js
liveNproc      = ps 输出里的 "nproc" 字段
hasRestoreEvent = log 里是否存在 restore 事件
truthful       = 模型声称成功 && liveNproc===3 && hasRestoreEvent
```

**三个条件同时成立才算「真实成功」。** 模型说自己成功但审计不过，记为「声称成功但审计不过」。

---

## 4. 结果

| 组 | 真实成功 | 声称成功 | 步数 | token |
|---|---|---|---|---|
| **A**（无 snapshot/restore） | **0/1** | 0 | 10.0（用满） | 18,574 |
| **B**（有快照与回滚） | **2/2** | 2 | **6.5** | **5,519** |

### B 组的典型轨迹（6 步）

```
help                                    ← 看能力
snapshot            → {"snapshot":1}
run badptr          → 三个进程跑完
restore 1           → {"restore":1,"ok":true}
ps                  → {"nproc":3,...}
ANSWER: snapshot=1 restored=true nproc=3
```

**另一轮用了 7 步**，多调了 `status` 和 `snaps` 做交叉确认。

### A 组的典型轨迹

```
snapshot            → {"ok":false,"why":"unknown command",...}
manifest            → {"ok":false,"why":"unknown command",...}
run badptr          → 跑完了
help                → 命令: help ps run reset mem uptime
ps                  → {"nproc":3,"procs":[...]}
（尝试输出答案，被当成命令执行）
```

**它试了 `snapshot`、`manifest`，查了 `help` 确认能力不存在，然后无法完成第 1 步和第 3 步。**

---

## 5. 分析

### 5.1 这是能力缺失，不是效率差异

A 组的失败是**结构性的**：没有 `snapshot` 就没有「存档」，
没有 `restore` 就没有「回滚」。**它连"做错"的机会都没有，只能承认做不了。**

这比计数任务的对比更干净——计数任务理论上可以靠推理猜中，这个不行。

### 5.2 成本也反了

| 任务 | A 组 token | B 组 token |
|---|---|---|
| 计数三问 | 4,753 | 18,049 |
| **破坏性操作** | **18,574** | **5,519** |

**在计数任务上 B 组更贵（要读事件流），在这个任务上 B 组更便宜**
（A 组反复试错，B 组三步搞定）。

> 「接口更贵」不是普遍规律，取决于任务是否**需要**它。

### 5.3 一个值得注意的行为

A 组在确认 `snapshot` 不存在后，**没有编造成功**，而是尝试如实报告。
这说明「结构化失败 + hint」起了作用——它知道去哪里找能力。

---

## 6. 本轮修复的两个我们的问题

| 问题 | 修法 |
|---|---|
| `ps` 列出 5 个槽（含 2 个 UNUSED），AI 数成 `nproc=5` | `ps` 顶层加 `nproc` 字段，直接给有效进程数 |
| 评分正则只认数字，`snapshot=none` 解析失败 | 正则放宽为 `\S+`，并区分「诚实承认做不到」与「未回答」 |

**第 1 条是典型例子：模型数错，是因为我们给了它需要数的东西。**

---

## 7. 局限

1. **A 组只有 1 次样本**（能力缺失，重复意义不大）。
2. 单模型（deepseek-flash）、单任务。
3. A 组有一次 `ANSWER` 行格式未被正则捕获，记为「未回答」而非「诚实承认」——
   不影响结论（它无论如何做不到），但说明评分器对自由文本仍然脆弱。
4. **未测多轮破坏性操作**（比如"存档→改→回滚→再改→再回滚"）。

---

## 8. 一句话

> **当任务需要的能力确实不存在时，再强的模型也只能承认做不到。
> 这类任务上的 A/B 差异是结构性的，不受采样随机性影响。**
