# 语言 / 计算引擎类项目选题调研

> 委托约束：Windows 全程开发、不做硬件、不做检测/分类/识别/抽取、尽量不依赖数据集、形态是"从零实现一个系统"、周期三个月、**必须有客观的"不通过就是失败"验收标准**。

> 本文所有【事实】均给出可点开的 URL；凡属推断一律标注【推测】；查不到证据的写"未找到"。

## 0. 结论先说

- **验收最硬、Windows 摩擦最小、最不容易"做完了没法证明"的两个方向**：
  1. **从零实现电子表格公式引擎 + 依赖图增量重算**，用 **Excel COM / LibreOffice 无头重算**做 oracle 逐单元格对拍（Windows 反而是优势）。
  2. **从零实现行级 diff + 三方合并 + 树级 diff**，用 **GNU diff / `git merge-file` 逐字节对拍 + 退出码**做验收（语义在官方文档里写得极死，几乎无法狡辩）。
- **验收同样硬但"太常见"**：从零写 C 子集编译器（c-testsuite 220 例）、Lox 解释器 + GC（266 例）。这两个是"稳但没新意"的代表。
- **新意高但三个月风险高**：WebAssembly 解释器 + 验证器（官方 spec 293 个 `.wast`，逐条 assertion 判分）。

## 2. 候选逐项

### 候选 1：从零实现 C 子集编译器（→ 自有字节码 / 机器码）

- **一句话系统描述**：把 C 的一个明确子集（无预处理器或仅 `#define`，无浮点，支持指针/结构体/函数调用）编译成自定义字节码，由自己写的 VM 执行；同一份测试用例可同时喂给 gcc 对拍。
- **5 个模块**
  1. 词法 + 预处理子集（宏、条件编译可砍）
  2. 递归下降语法分析 → AST（含类型标注）
  3. 类型检查（隐式转换、指针算术、结构体布局）
  4. 代码生成（字节码 + 栈帧/调用约定）与运行时（`printf`、`malloc` 子集）
  5. 测试驱动：TAP 解析器 + 差分对拍脚本 + 失败分类报告
- **客观验收方式**
  - **测试集通过率**：`c-testsuite` 的 `single-exec` 套件，**220 个用例**（TAP 计划行 `1..220`）；判定规则官方写死：`$t.c.expected` 必须与程序 stdout+stderr **完全一致**，且程序 exit 0，单例超 5 分钟算失败 → 这已经是"逐字节"级别。【事实·已核：README https://github.com/c-testsuite/c-testsuite ，报告 https://c-testsuite.github.io/gcc-x86_64-single-exec_report.tap.txt 我抓取当日为 216 ok / 4 not ok】
  - **补充测试集**：chibicc 自带 `test/` 下 **41 个 `.c`** 用例（我按仓库树统计）。【事实·已核】
  - **自举（bonus，最漂亮的演示材料）**：用你的编译器编译你自己的编译器源码并跑同一套测试。chibicc 自述可编译 Git、SQLite、libpng 及自身且通过其测试套件。【事实·文档：https://github.com/rui314/chibicc 】
  - **软验收部分**：代码质量、错误信息友好度——不要写进硬指标。
- **体量估计**：核心 4k–6k 行（无预处理器、无浮点）；做到接近 chibicc 的 C11 覆盖是 8k–10k 行。【推测】
- **现成参照物（这是它最大的优势）**
  - chibicc：**每个 commit 对应书的一节**，等于一份"分步教程 + 可运行参考实现"，11,952 stars。【事实·已核】
  - Ghuloum《An Incremental Approach to Compiler Construction》：http://scheme2006.cs.uchicago.edu/11-ghuloum.pdf 【事实·文档，chibicc README 引用】
  - Crafting Interpreters（对比字节码 VM 设计）：http://craftinginterpreters.com/
- **最可能翻车**
  - Windows 目标：chibicc 自述开发平台是 Ubuntu 20.04 x86-64，"portability is not my goal"，输出 AT&T 汇编再调 `cc`/`as`。【事实·文档】→ 在 Windows 上要么改后端为自有字节码（推荐），要么装 MinGW/MSYS2。
  - `c-testsuite` 的 runner 依赖 **posix sh + python3 + coreutils**。【事实·文档】Windows 上得用 Git Bash / MSYS2 跑，属于"能跑但别指望零摩擦"。
  - 结构体传参 ABI、可变参数、`long double` 是无底洞——必须在开题时**书面砍掉**。
- **Windows 可行**：**可行，但取决于后端选择**。自有字节码 VM：纯计算，零问题；x86-64 机器码 + PE 可执行文件：三个月内属于自杀。【推测】

### 候选 2：从零实现解释器 + 垃圾回收器

- **一句话系统描述**：实现一门小语言（可直接用 Lox）的字节码解释器，并自研标记-清除（可选三色增量/分代）GC，用官方 Lox 测试套件验收语言语义，用压力测试验收 GC。
- **5 个模块**
  1. 词法/语法/AST 或单遍字节码编译
  2. 值表示与对象模型（字符串驻留、闭包、upvalue）
  3. 字节码 VM / 调用栈 / 异常与栈展开
  4. GC：分配器、根集合（栈+全局+闭包）、标记、清除/压缩
  5. 测试驱动：`// expect:` 注释解析器 + GC 压力模式（强制每次分配都触发 GC）
- **客观验收方式**
  - **测试集通过率**：Crafting Interpreters 官方 `test/` 下 **266 个 `.lox`** 文件（我按仓库树统计），每个文件用 `// expect:` / `// expect runtime error:` 注释声明期望输出，套件自带 runner 语义。【事实·已核：https://github.com/munificent/craftinginterpreters/tree/master/test 】
  - **GC 正确性**：把"强制 GC（每次分配触发）与不强制 GC 的输出必须逐字节一致"作为硬断言——这是可自动化的。
  - **GC 有效性**：堆峰值/总分配字节数下降比例（阈值自定）；`-Xmx` 式配额下程序仍能跑完。
  - **无悬垂/泄漏**：Windows 上没有 Valgrind，只能用 Dr. Memory 或 CRT debug heap（`_CrtSetDbgFlag`）。
  - **判定性质**：语言语义部分是**硬验收（测试集通过率）**；GC 部分是**半软**——"GC 好不好"没有官方测试集，只能靠"压力下不崩 + 峰值下降"这两个可测代理指标。**这一点必须提前跟导师讲清楚**，否则演示时会被问"你怎么证明你的 GC 是对的"。
- **体量估计**：3k–5k 行（clox 量级）。【推测】
- **现成参照物**：Crafting Interpreters 免费在线全书（含 GC 一章）http://craftinginterpreters.com/ ；仓库 11,119 stars。【事实·已核】
- **最可能翻车**：GC bug 是概率性的，表现为"跑一千次崩一次"，调试成本极高；Windows 缺 Valgrind 类工具会放大这一点。
- **Windows 可行**：**完全可行**（纯计算，无平台依赖）。

### 候选 3：从零实现 SQL 查询引擎（含查询优化器）

- **一句话系统描述**：自己实现页式存储 + B+ 树索引 + SQL 解析 + 火山模型执行器 + 基于代价的优化器（谓词下推、索引选择、join 顺序），用 SQLite 与官方 sqllogictest 数据对拍。
- **5 个模块**
  1. 存储层：页管理、B+ 树、记录编解码、简单 WAL 或事务（可砍）
  2. 前端：SQL 词法/语法 → AST，schema/catalog
  3. 执行器：scan/filter/project/sort/join/aggregate 算子与迭代器模型
  4. 优化器：逻辑改写（谓词下推、投影裁剪）+ 代价模型 + 计划选择
  5. 测试驱动：sqllogictest 解析/执行器 + SQLite 结果对拍
- **客观验收方式**
  - **测试集通过率（首选）**：`sqllogictest`（SLT）是数据库界的 de-facto 一致性格式，官方口径为 **720 万条查询 / 1.12GB 测试数据**，且其设计目的就是"用另一个独立引擎生成参考答案再比对"。【事实·文档：https://www.sqlite.org/testing.html 】
  - **可获取的数据**：GitHub 镜像 `gregrahn/sqllogictest`（337MB，**622 个 `.test` 脚本**，含 `test/`、`src/`、`proto/`，`about.wiki` 说明 completion / validation 两种模式与 `-verify`）。【事实·已核：https://github.com/gregrahn/sqllogictest 】
  - **与成熟实现对拍**：同一份 SQL 分别喂给你的引擎和 SQLite，比结果集（用 `ORDER BY` 固定顺序；SLT 本身对值做哈希、对行序有规定，需按格式实现）。
  - **优化器的验收要小心**：正确性 = "开/关优化器结果集完全一致"（这是硬断言，SQLite 自己就是这么测的，见 testing.html 第 9 节"Disabled Optimization Tests"）；"优化有效"只能靠性能指标（延迟/扫描行数），属**软验收**。
  - **判定性质**：结果正确性=硬；优化器收益=软。**必须把两者在演示 PPT 上分开写**。
- **体量估计**：5k–8k 行（含 B+ 树与优化器）。【推测】
- **现成参照物**
  - `cstack/db_tutorial`《Let's Build a Simple Database》：13 个 part，10,536 stars，从 REPL 写到 B 树——但**没有优化器**，正好是你加料的位置。【事实·已核】
  - SQLite 官方文档（文件格式、类型亲和性）。
  - SLT 规范（镜像里的 `about.wiki`）。【事实·已核】
- **最可能翻车**：SQL 类型亲和性/比较规则、NULL 三值逻辑、浮点与文本输出格式（SLT 对输出格式极敏感，格式错会被判"错"）；SQL 方言范围失控。
- **Windows 可行**：可行（C/C++/Rust/Python 纯计算；SQLite CLI 有 Windows 版可直接当 oracle）。

### 候选 4：从零实现电子表格公式引擎（依赖图 + 增量重算）★ 推荐

- **一句话系统描述**：实现一个 Excel 公式子集的计算引擎：解析公式、构建单元格依赖图、全量求值与**只重算受影响子图**的增量求值，并把每个单元格的结果与 Excel/LibreOffice 的重算结果逐格对拍。
- **5 个模块**
  1. 公式解析器：Excel 文法（中缀、`%`、`^`、比较运算、`&`、区域引用 `A1:B10`、绝对/相对引用、跨表引用）
  2. 值模型：double / int / string / bool / error（`#DIV/0!`、`#VALUE!`、`#REF!`、`#NAME?`、`#NUM!`、`#N/A`）+ 空单元格语义 + 类型强制转换规则
  3. 函数库：分三批交付（数学/逻辑/文本 60 个 → 查找引用 20 个 → 日期/财务 20 个），每个函数独立验收
  4. 依赖图与增量重算：脏标记 + 拓扑序 + 环检测（迭代计算）+ **重算单元格计数器**
  5. 对拍驱动：随机工作簿生成器 + Excel COM / LibreOffice 无头重算 + 逐单元格 diff 报告
- **客观验收方式（本方向最强的地方）**
  - **与成熟实现对拍，判定到单元格级**：
    - Excel 路径（Windows 原生优势）：`Application.Calculate` 官方文档存在，可用 pywin32 调 COM 强制重算再读值。【事实·文档：https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculate 】
    - LibreOffice 路径：安装 StarBasic 宏 `ThisComponent.calculateAll()` 后无头调用 soffice，是现成可抄的做法（`anthropics/skills` 里的 `recalc.py` 就是这么干的，且显式 `import platform`）。【事实·已核：https://github.com/anthropics/skills/blob/main/skills/xlsx/scripts/recalc.py 】→ 但**在 Windows 上跑通的具体命令我没实测**，标【待实测】。
  - **不需要数据集**：工作簿由你随机生成（随机公式 + 随机常量 + 随机引用拓扑），用例数无上限。这直接命中"不需要数据集是巨大加分项"。
  - **自洽性金标准（这条最硬且零外部依赖）**：对任意编辑序列，**增量重算结果 ≡ 全量重算结果**，逐单元格 bit 相等。这条可以完全自动化、永真、不依赖 Excel。
  - **性能/正确性双指标**：改一个单元格后"实际重算的单元格数"必须等于依赖图闭包大小（用计数器断言，防止偷偷全量重算）；10^5 单元格重算耗时。
  - **判定性质**：**硬验收为主**（逐格比对 + 自洽性 + 重算计数），只有"UI 好不好用"是软验收。
- **体量估计**：4k–7k 行（150 个函数 + 依赖图 + 增量）。【推测】
- **现成参照物**
  - HyperFormula（2,821 stars，**400+ 公式**的无头电子表格引擎）可作函数语义参考。【事实·已核】
  - 三引擎差异实测库：`canispreadsheet.com` 声称已执行 **2,334 个用例**，并给出"LibreOffice 在 135 个函数、272 个用例上把文档里的 `#NUM!/#N/A/#DIV/0!/#REF!` 统一报成 `#VALUE!`"这类硬数据，附 GitHub 数据集 `xxAFLabsxx/spreadsheet-compat`（21MB，1 star，属小众项目，**不能当标准，只能当参考**）。【事实·已核：https://canispreadsheet.com/guides/ 】
  - LibreOffice 各版本函数支持差异（如 `VSTACK/TEXTSPLIT` 直到 25.8.7.3 才可用）也在同一站点。【事实·已核】
- **最可能翻车**
  - **oracle 不唯一**：Excel / Google Sheets / LibreOffice 三者语义有实测分歧（上面那批差异），所以**开题时必须钉死"以谁为准 + 哪个版本"**，否则同一格能有三个"正确答案"。
  - 浮点显示与比较（15 位有效数字）、日期序列值（1900 闰年 bug）、数组/动态数组公式，任何一项都能吞掉两周。
  - 动态数组、`INDIRECT`/`OFFSET` 这类会破坏依赖图静态性的函数，建议直接列为"不支持"。
- **Windows 可行**：**最优**。Excel COM 是 Windows 原生 oracle；无 Excel 时退化为 LibreOffice（跨平台）。这是九个方向里唯一"Windows 反而是加分项"的。

### 候选 5：从零实现增量计算引擎（Salsa / Adapton 形态）

- **一句话系统描述**：实现一个"查询图"增量计算框架：输入变更后只重算受影响的查询，并支持早截断（early cutoff）与循环不动点；用一个真实小系统（如迷你构建系统或迷你 IDE 分析器）证明它有效。
- **5 个模块**
  1. 查询注册与 memo 表（key → value + 依赖集）
  2. 修订/版本管理与失效传播
  3. 验证阶段（依赖未变则复用）+ 早截断
  4. 循环检测与不动点迭代
  5. 可观测性与驱动：执行事件计数、随机编辑序列对拍、演示应用
- **客观验收方式**
  - **与 naive 全量重算对拍**：随机编辑序列下，增量结果必须与"每次从零全量算"结果完全一致（硬断言，无需数据集）。
  - **重算次数断言**：改一个输入，只允许重算依赖闭包内的 N 个查询——Salsa 的 `EventKind` 明确提供 `WillExecute`（真要重算）与 `DidValidateMemoizedValue`（验证后复用）事件，说明"重算次数可观测、可断言"。【事实·已核：https://docs.rs/salsa/latest/salsa/enum.EventKind.html 】→ 这是本方向把"软"变"硬"的关键设计。
  - **性能**：与全量重算的耗时比。
  - **判定性质**：**硬**（一致性 + 计数），但"系统感"弱。
- **体量估计**：核心 2k–3k 行 + 演示应用。偏小。【推测】
- **现成参照物**
  - Salsa：3,000 stars，官方 book 有**中文版** https://rust-chinese-translation.github.io/salsa-book ，README 明确点名灵感来自 Adapton / Glimmer / rustc query system。【事实·已核】
  - 《Build Systems à la Carte》(ICFP'18)：把"重算策略"抽象成可组合组件，附可执行代码 `snowleopard/build`（281 stars）。【事实·已核：https://www.microsoft.com/en-us/research/publication/build-systems-la-carte/ 】
- **最可能翻车**：演示时被问"这不就是个带缓存的求值器吗"；演示效果平淡（没有可见产物）；早截断/循环语义微妙，容易只做对 happy path。
- **Windows 可行**：完全可行（若选 Rust，Windows 上 cargo 无障碍）。

### 候选 6：从零实现正则表达式引擎

- **一句话系统描述**：实现 `pattern → NFA(Thompson) → 线性时间模拟 → 惰性 DFA 缓存` 的正则引擎，支持子匹配/贪婪语义，并用多引擎共享测试集与性能基准验收。
- **5 个模块**
  1. 语法解析（字面量、字符类、`*+?{n,m}`、分组、交替、锚点）
  2. Thompson 构造 → NFA（状态集、ε 闭包）
  3. 线性时间 NFA 模拟（state list + generation 标记）
  4. 子匹配/贪婪优先级 + 可选的惰性 DFA 缓存
  5. 测试/差分/基准驱动
- **客观验收方式**
  - **测试集通过率**：`rust-lang/regex` 的 `testdata/` 下 **52 个 TOML 测试文件**（我按仓库树统计），README 明确"一套测试驱动多个引擎"，并有 `regex-test` crate 规定格式。【事实·已核：https://github.com/rust-lang/regex/tree/master/testdata 】
  - **差分对拍**：与 Python `re` / RE2 在**共有语法子集**上随机生成 pattern+input 对拍（先冻结语法白名单，否则差异全来自语法而非 bug）。
  - **线性时间硬断言（这是最漂亮的客观指标）**：用经典病态模式 `a?^n a^n` 对 `a^n`，n=25/29/100 的耗时必须是多项式增长（回溯引擎在 n=29 就要 60 秒以上）。Russ Cox 文章给了完整论证与 <400 行 C 参考实现。【事实·已核：https://swtch.com/~rsc/regexp/regexp1.html 】
  - **性能基准**：BurntSushi 的正则基准项目（rebar）可作横向对比（具体基准集我未逐项核实）。【事实·文档级/待核】
- **体量估计**：3k–5k 行（含 DFA 缓存与 Unicode 可选项）。【推测】

### 候选 8：从零实现 diff / 三方合并（行级 + 树级）★ 推荐

- **一句话系统描述**：实现 Myers diff（含 `--minimal` 与 patience/histogram 变体）、统一格式输出、diff3 风格三方合并、以及目录/文件树级 diff，全部与 GNU diff / git 逐字节对拍。
- **5 个模块**
  1. 行级 diff 核心（Myers O(ND) + 最小化）
  2. 统一格式渲染（hunk 头、上下文行、`\ No newline at end of file` 等边界）
  3. 三方合并（base/ours/theirs → 冲突标记 + 冲突计数）
  4. 树级 diff（目录遍历、重命名检测、按内容哈希配对）
  5. 对拍驱动：随机文件/随机编辑生成器 + GNU diff / git 调用 + 逐字节比对
- **客观验收方式（九个方向里最干净）**
  - **与 GNU diff 逐字节一致**：固定参数（如 `diff -u`、对照 `diff -u --minimal`）后比较完整输出。注意：GNU 默认不保证最小编辑脚本，`--minimal` 才保证——所以"逐字节"必须**先钉死参数集**。
  - **与 `git merge-file` 逐字节一致**：官方文档把语义写死了——冲突用 `<<<<<<< / ======= / >>>>>>>` 包裹，支持 `--diff3`、`--zdiff3`、`--marker-size`、`--diff-algorithm={patience|minimal|histogram|myers}`，**退出码 = 冲突数**（>127 截断为 127，干净合并为 0）。【事实·文档：https://git-scm.com/docs/git-merge-file 】→ 这等于给了你一个"输出 + 退出码"双重可判定的 oracle。
  - **随机对拍，无需数据集**：随机生成 base 与两路编辑，跑 oracle 与你的实现，逐字节比。
  - **参照测试脚本**：diffutils 镜像 `tests/` 下 19 个条目（含 `basic`、`binary`、`filename-quoting`、`function-line-vs-leading-space` 等）；git 仓库 `t/` 下 **2,017 个测试脚本**（我按仓库树统计）。【事实·已核：https://github.com/Distrotech/diffutils/tree/master/tests 】
  - **性能**：1MB 文件、10 万行、极端相似/极不相似两种输入的耗时曲线。
  - **判定性质**：**全硬**。没有一条需要主观打分。
- **体量估计**：行级 1.5k–3k 行；加树级 + 三方合并 + 多算法 → 3k–4k 行。**这是它唯一的弱点：偏小。**【推测】
- **现成参照物**：git-merge-file 官方文档（语义规范）；diffutils 手册与测试；Myers 1986 论文；patience diff（Bram Cohen）思路。
- **最可能翻车**
  - **体量被质疑**：解法是主动加料——`--diff-algorithm` 三算法切换、树级 diff + 重命名检测、三方合并的冲突解决策略（`--ours/--theirs/--union`）、以及一个前端可视化合并 UI（正好用上委托人的前端功底）。
  - Windows 的 CRLF / 编码：必须统一按 LF + UTF-8 处理输入，否则 oracle 和你自己的换行处理不一致，对拍会假失败。
  - GNU 的启发式（速度优化）会让"最优解不唯一"，所以要用 `--minimal` 档位做严格对拍、默认档位做宽松对拍。
- **Windows 可行**：**最顺**。Git for Windows 自带 GNU diff 与 `git merge-file`，不用装 Linux 工具链（PATH 需确认，未逐项实测）。

### 候选 9（额外）：从零实现 WebAssembly 解释器 + 验证器

- **一句话系统描述**：实现 wasm 二进制解码、类型栈验证器与解释执行器（i32/i64/f32/f64、内存、表、间接调用），用官方 spec 测试套件逐条 assertion 判分。

## 5. 我认为最好的两个

### 第一名：表格公式引擎 + 依赖图增量重算（候选 4）

**为什么是它**

1. **验收是"逐单元格对拍"级别的硬指标**，而且同时具备三重独立判据：
   - 外部 oracle：Excel COM `Calculate`（Windows 原生）/ LibreOffice 无头 `calculateAll()`；
   - 内部金标准：**增量重算 ≡ 全量重算**（bit 级，无需任何外部依赖，永真）；
   - 过程指标：**重算单元格数 == 依赖闭包大小**（防作弊，防"偷偷全量算"）。
2. **完全不需要数据集**：随机工作簿生成器就是数据集，用例无限。
3. **Windows 是优势而非负担**：唯一一个"装个 Office 就得到工业级 oracle"的方向。
4. **正好用上委托人的前端 / 可视化功底**：Web 表格 UI + 依赖图可视化 + 重算热力图，演示效果远好于终端里跑测试。
5. **常见程度低但有"系统感"**：不像"增量计算引擎"那样容易被说成"一个缓存库"，它有 UI、有引擎、有算法。
6. **三个月节奏清晰**：M1 解析器 + 值模型 + 60 函数 + 全量求值（可演示）；M2 依赖图 + 增量重算 + 自洽性测试（核心创新点）；M3 对拍驱动 + 函数扩到 150 + 前端 UI + 报告。
7. **可写进论文的"技术点"**：增量重算的最小重算集、环检测与迭代计算、错误值传播、以及"三引擎语义差异"的实测对比（这一条本身就能凑一章）。

**风险与对冲**：oracle 必须**开题时钉死**（建议"以本机 Excel 版本为准，LibreOffice 仅作参考"），因为三引擎实测存在分歧（LibreOffice 有 272/2334 个用例错误码与微软文档不一致）。函数集必须**书面冻结**，动态数组/`INDIRECT`/`OFFSET` 明确不支持。

### 第二名：diff / 三方合并 + 树级 diff（候选 8）

**为什么是它**

1. **这是全清单里"最不可能被狡辩"的验收**：`git merge-file` 的输出格式、冲突标记、`--diff3` 变体、以及"退出码 = 冲突数"全部写在官方文档里；GNU diff 的 `-u` 输出也是确定性的。逐字节比 + 退出码比，过了就是过了。【事实·文档】
2. **三个月可行性最高**：行级 core 两周能跑通第一版，后面全是"加算法 / 加树级 / 加 UI"的增量工作，不存在"到第三个月还在调解析器"的风险。
3. **Windows 零摩擦**：Git for Windows 直接提供 oracle，不需要 MSYS2 编译工具链、不需要改后端、不需要装 Office。
4. **常见程度最低之一**（`three-way merge` 仅 12 个仓库），且"写 diff"在评审眼里是实打实的算法功底，不是调库。
5. **有天然的加料路径**（解决它唯一的弱点——体量偏小）：
   - `--diff-algorithm` 三算法（myers / patience / histogram）并给出各自的对拍通过率；
   - 树级 diff + 重命名检测（对拍 `git diff --raw`）；
   - 冲突解决策略 `--ours/--theirs/--union` + 交互式合并；
   - 前端可视化三方合并 UI（委托人前端背景直接变现）；
   - 性能曲线（1MB / 10 万行）。
6. **演示叙事极强**："我的实现在 12,000 组随机用例上与 GNU diff / git merge-file **逐字节一致**，并且在 X 组上比 git 更快"——这句话没有任何主观成分。

**风险与对冲**：一定要在开题报告里把"体量"讲成"算法族 + 树级 + UI"三块，否则会被说"就是个 diff"；同时固定 LF 处理，避免 Windows 换行把对拍搞成假失败。
